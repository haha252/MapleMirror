# M1 基础骨架详细设计

> 状态：已确认，进入 M1 实现（确认日期：2026-05-27）
> 阶段：M1 基础骨架  
> 需求基线：`docs/开发要求.md` 定稿 v1.0（2026-05-27）  
> 文档作用：将 M1 可实施范围和为后续阶段预留的数据合同明确化；若本文与需求基线存在冲突，以需求基线为准。

## 1. 本阶段必须满足的要求

### 1.1 M1 交付边界

M1 实现经确认后仅交付以下基础能力：

| 类别 | 必须交付 |
| --- | --- |
| 程序骨架 | `master` 主节点与 `node` 下载节点两个可执行程序，入口只负责装配依赖 |
| 配置 | 主节点和下载节点 YAML 加载、默认值、关键字段校验、中文示例注释与 UTF-8 读写 |
| 日志 | `debug`、`info`、`warn`、`error` 四等级，控制台/文件独立阈值，按日切分、保留周期配置 |
| 请求 ID | 主节点每个 HTTP 请求生成不可预测 ID，响应返回 `X-Request-ID`，日志可关联 |
| 持久化 | 主节点 SQLite 初始化与迁移机制，为授权、额度、库存、统计等后续阶段能力保留事务化存储结构 |
| 健康检查 | 主节点和下载节点提供中文健康响应；不得冒充尚未实现的业务能力 |
| 构建 | `scripts/build-windows.bat` 与 `scripts/build-linux-amd64.sh` 方案，最终输出两个二进制和中文注释配置示例 |
| 质量门禁 | 配置、日志、请求 ID、迁移、编码和跨平台构建的聚焦测试；源码及前端资源行数检查方案 |

### 1.2 从首版合同继承的不可变约束

即使具体业务在 M2 至 M6 才实现，M1 的结构和存储不得妨碍以下定稿规则：

| 主题 | 不可变约束 |
| --- | --- |
| 架构 | 首版为单一主节点；下载节点不能绕过主节点签发公共下载授权 |
| 仓库与摘要 | 仅公开 GitHub 仓库；正式版与预发布版均可配置；资产缺少 `sha256:` 摘要或算法不符必须拒绝镜像 |
| 副本和路由 | 每个下载节点应持有保留窗口内全部可服务资产；新节点最终对账完成前不得参与公共下载路由 |
| 网页验证 | 仅自托管 ALTCHA，默认工作量档位为“中等”，不得叠加滑块或网页自研前导零 PoW |
| 公开 API | 不设账号和 API Key；使用 SHA-256 前导零 PoW，默认 `23` 位二进制前导零 |
| 管理安全 | 无管理前端；管理 API 仅管理网络可访问并使用强随机管理令牌；高风险节点操作必须叠加 mTLS |
| 额度 | IPv4 同时约束 `/32`、`/24`，IPv6 同时约束 `/128`、`/64`；倍率仅扣请求额度 |
| 流量 | 每日与累计流量只按下载节点实际发送字节计量；签发前须原子预留流量预算 |
| 次数统计 | 对外“下载授权次数”在成功签发令牌时加一；内部另存“开始传输授权数” |
| 请求关联 | 请求 ID 必须贯穿挑战、授权、节点下载、流量上报和控制面排障链路 |
| 界面及文本 | 页面、错误信息、日志、配置注释和文档使用中文；代码标识符和协议字段可用英文 |
| 编码与规模 | 文本统一 UTF-8；Markdown 只放 `docs/` 且不限 250 行；源码和前端资源原则上单文件不超过 250 行 |

### 1.3 M1 明确不实现的功能

以下事项只做结构兼容或数据表预留，不在 M1 提供可用业务接口：

- 节点配对、mTLS 控制通道、心跳和管理 API 操作，属于 M2。
- GitHub Release 扫描、摘要验证、资产同步和新节点追平，属于 M3。
- 四个公共页面、ALTCHA、公开 API PoW、下载令牌和 Range 文件下载，属于 M4。
- 额度实际扣减、流量入账、统计展示和 SLA 展示，属于 M5。
- 完整协议与部署交付、安全及性能验收，属于 M6。

健康页只能报告进程、配置和数据库基础就绪状态，不提供“节点在线”“资产可下载”之类尚未实现的结论。

## 2. 设计原则与运行形态

### 2.1 进程职责

| 程序 | M1 职责 | 启动输入 | 基础输出 |
| --- | --- | --- | --- |
| `mirror-master` | 装载主节点配置、初始化日志和 SQLite、提供健康 HTTP 服务 | `config.yaml`，可选的 `projects.yaml`/`quota.yaml` 结构校验 | 中文日志、SQLite 文件、`/healthz` 中文 JSON |
| `mirror-node` | 装载节点配置、初始化日志、提供本地健康 HTTP 服务 | `node.yaml` | 中文日志、`/healthz` 中文 JSON |

M1 不启动任何伪控制面连接或模拟下载路由。后续服务仅通过接口注入到入口装配层。

### 2.2 分层规则

| 层级 | 责任 | 禁止事项 |
| --- | --- | --- |
| 入口层 | 解析启动参数、加载配置、组装服务、响应退出信号 | 写业务判断或直接拼 SQL |
| 配置层 | YAML 映射、默认值、验证、示例生成、UTF-8 I/O | 在 HTTP 处理器中散落默认值 |
| 基础设施层 | 日志、请求 ID、中间件、SQLite 连接和迁移 | 对授权或统计口径自行作决定 |
| 领域合同层 | 类型、枚举、时间/字节/状态等共享合同 | 依赖具体 HTTP 路由或页面 |
| 传输层 | M1 仅健康端点，后续扩展公开/管理/控制协议 | 把持久化细节直接暴露为响应 |

### 3.1 文件规模控制

- `main.go` 仅做依赖装配与生命周期控制，不承载健康处理器或迁移 SQL。
- 配置按文件合同拆分，日志与请求 ID 单独成包，避免单文件累积业务职责。
- 初始迁移文件属于 SQL 维护文件；若超过 250 行，拆分为同一版本事务中的按领域迁移片段，执行器按固定顺序加载。
- M4 引入 `web/` 后按页面、组件、样式和请求客户端拆分资源，并将行数检查覆盖该目录。

## 4. 配置合同设计

### 4.1 共同规则

| 规则 | 设计 |
| --- | --- |
| 文件编码 | 配置示例生成与读取固定使用 UTF-8，不依赖系统代码页 |
| 初次生成 | 找不到配置文件时生成带中文注释的示例配置，并提示用户确认关键安全字段后启动 |
| 缺失字段 | 非安全关键字段应用默认值，并写中文 `warn` 日志说明字段和采用值 |
| 非法关键字段 | 监听地址、管理保护、TLS 路径、数据库路径、网段、时区、令牌密钥来源等非法时拒绝启动 |
| 敏感值 | 管理令牌、签名密钥、私钥不写入示例明文，不写入普通日志；配置只引用环境变量名或凭据文件路径 |
| 时间格式 | YAML 中持续时间使用 Go 可解析文本，例如 `30s`、`15m`、`48h` |
| 容量格式 | 示例中使用可读 GiB 表述，加载后规范化为字节整数进行存储和比较 |

## 5. SQLite 初始数据库设计

### 5.1 设计目标

- 主节点使用 SQLite，开启外键，并通过事务支持后续“签发前原子预留流量预算”。
- M1 执行首个迁移以建立稳定的表和索引合同；后续阶段只以新迁移扩展，不在运行中临时改表。
- 时间字段统一保存 UTC 时间文本或整数时间戳，由展示/日聚合逻辑依据配置时区 `Asia/Shanghai` 解释统计日。
- IP 不在普通日志保存完整值；数据库中为了额度准确性存储规范化前缀键，访问与展示必须受控。
- 令牌密文、管理令牌和证书私钥不存入普通业务表。

### 5.2 迁移与基础表

| 表 | 关键字段 | 用途 |
| --- | --- | --- |
| `schema_migrations` | `version` PK, `applied_at` | 记录迁移版本，M1 启动即使用 |
| `runtime_kv` | `key` PK, `value`, `updated_at` | 保存非敏感运行游标，例如扫描条件请求游标的扩展定位 |

### 5.3 项目、版本与资产库存表

| 表 | 关键字段 | 约束与说明 |
| --- | --- | --- |
| `projects` | `id` PK, `name`, `repository`, `enabled`, `retain_versions`, `include_prerelease`, `download_multiplier`, `config_hash`, `updated_at` | 从 `projects.yaml` 投影；倍率仅被额度逻辑使用 |
| `releases` | `id` PK, `project_id` FK, `github_release_id`, `tag_name`, `prerelease`, `published_at`, `selected`, `created_at` | 同项目下 GitHub Release ID 唯一 |
| `assets` | `id` PK, `release_id` FK, `github_asset_id`, `file_name`, `architecture`, `size_bytes`, `source_url`, `digest_sha256`, `service_state`, `created_at` | `digest_sha256` 只接受已验证的 `sha256:` 合同来源；无可信摘要不得进入可服务状态 |
| `target_inventory` | `node_id` FK, `asset_id` FK, `desired_state`, `updated_at` | 每节点每目标资产一行，支撑全节点副本策略 |
| `node_inventory` | `node_id` FK, `asset_id` FK, `local_digest_sha256`, `size_bytes`, `verified_at`, `state` | 只有摘要校验通过的记录才能用于未来路由 |

建议索引：

- `releases(project_id, published_at)` 与 `assets(release_id, service_state)` 支撑扫描选择及查询。
- `target_inventory(node_id, desired_state)` 与 `node_inventory(node_id, state)` 支撑节点对账。

### 5.4 节点、任务与审计表

| 表 | 关键字段 | 约束与说明 |
| --- | --- | --- |
| `nodes` | `id` PK, `public_name`, `certificate_fingerprint`, `state`, `target_bandwidth_bps`, `last_heartbeat_at`, `routing_ready`, `created_at`, `updated_at` | `routing_ready` 在最终对账完成前必须为假 |
| `pairing_codes` | `id` PK, `code_hash`, `expires_at`, `used_at`, `created_by_request_id` | 仅存一次性码摘要，不保存明文 |
| `node_tasks` | `id` PK, `node_id` FK, `task_type`, `asset_id` FK nullable, `state`, `request_id`, `created_at`, `completed_at` | 同步、清理、撤销等控制任务的关联基础 |
| `node_heartbeats` | `id` PK, `node_id` FK, `state`, `pressure_ratio`, `active_downloads`, `free_bytes`, `reported_at` | 后续状态和 SLA 的原始心跳基础 |
| `admin_audit_events` | `id` PK, `operation`, `target_type`, `target_id`, `result`, `request_id`, `created_at` | 不写管理令牌或私钥；为危险操作审计预留 |

### 5.5 验证、授权、额度与流量表

| 表 | 关键字段 | 约束与说明 |
| --- | --- | --- |
| `challenges` | `id` PK, `kind`, `asset_id` FK, `client_prefix_key`, `nonce_hash`, `difficulty`, `expires_at`, `consumed_at`, `request_id` | `kind` 区分 `altcha` 与 `api_pow`，不得混用参数含义 |
| `download_authorizations` | `id` PK, `asset_id` FK, `node_id` FK, `client_prefix_key`, `issued_at`, `expires_at`, `max_bytes`, `range_limit`, `status`, `request_id`, `first_transfer_at` | 成功插入签发记录即代表一次“下载授权次数”；`first_transfer_at` 首次填写即代表一次内部开始传输 |
| `quota_buckets` | `scope_kind`, `scope_key`, `tokens_microunits`, `updated_at` | 同时支撑地址与网段请求桶；倍率只改变令牌消耗 |
| `traffic_reservations` | `authorization_id` PK, `scope_day`, `address_reserved_bytes`, `network_reserved_bytes`, `settled_bytes`, `status`, `created_at` | 签发事务内原子预留，实际字节结算 |
| `traffic_events` | `node_id` FK, `event_sequence`, `authorization_id` FK, `node_request_id`, `master_request_id`, `sent_bytes`, `reported_at`, `accounted_at` | `(node_id, event_sequence)` 唯一，保证断线补报幂等 |
| `daily_traffic_stats` | `stat_day`, `scope_kind`, `scope_key`, `sent_bytes`, `updated_at` | 仅按实际字节汇总；统计日受配置时区控制 |
| `daily_project_stats` | `stat_day`, `project_id`, `authorization_count`, `transfer_started_count`, `sent_bytes` | 明确分离两种次数 |
| `node_availability_samples` | `node_id`, `sample_start`, `sample_end`, `routable`, `heartbeat_ok` | M5 计算 `24h`、`7d`、`30d` SLA |

关键事务合同：

1. 后续签发下载令牌时，在同一事务内校验请求桶、按项目倍率扣减请求令牌、检查并预留地址及网段日流量、写入 `download_authorizations`。
2. `download_authorizations` 插入成功即累计“下载授权次数”，与客户端是否真正传输无关。
3. 首条正数字节的幂等 `traffic_events` 入账时，只允许首次设置 `first_transfer_at` 并累计一次“开始传输授权数”。
4. 每个已确认的流量事件按真实 `sent_bytes` 结算预留和统计；倍率不得参与流量数值计算。

### 5.6 初始迁移安全要求

- 数据库创建目录、数据库文件和 WAL 相关文件的失败均返回中文错误并拒绝继续服务。
- 迁移在事务中执行；失败不得把健康状态标为就绪。
- 初始索引至少覆盖唯一幂等键、授权关联、节点库存差异及按日聚合检索。
- 健康页只披露“数据库已连接/迁移已完成”等非敏感状态，不返回数据库绝对路径。

### 5.7 下载节点本地状态库

下载节点以文件系统保存资产；为满足断线后的事件补报与本地库存恢复，节点另使用 `storage.state_db` 指向的本地 SQLite 状态库。M1 只建立迁移和健康检查，后续阶段写入业务状态。

| 表 | 关键字段 | 用途 |
| --- | --- | --- |
| `schema_migrations` | `version` PK, `applied_at` | 下载节点本地迁移版本 |
| `local_assets` | `asset_id` PK, `relative_path`, `digest_sha256`, `size_bytes`, `verified_at`, `state` | M3 记录已校验资产；绝对磁盘路径不得上报公共页面 |
| `pending_traffic_events` | `event_sequence` PK, `authorization_id`, `node_request_id`, `master_request_id`, `sent_bytes`, `created_at`, `confirmed_at` | M5 在主节点确认前持久保存真实流量事件，重连后按序补报 |

节点事件只有在主节点明确确认幂等入账后才能清理；资产文件仍须在摘要通过后采用临时文件加原子替换进入可服务库存。

## 6. 日志设计

### 6.1 输出规则

| 项目 | 设计 |
| --- | --- |
| 等级 | 固定 `debug`、`info`、`warn`、`error`，配置只能在四者中选择 |
| 格式 | 结构化日志，中文消息正文加稳定英文键字段，便于程序检索 |
| 文件 | UTF-8 编码，按自然日切分，目录和保留天数由 YAML 配置 |
| 时区 | 日志显示时间明确包含偏移；按日文件边界采用配置的统计时区或文档明确的本地时区策略，在实现前固定为同一策略 |
| 控制台 | 支持独立阈值；Windows 运行和查看文档明确使用 UTF-8 |
| 脱敏 | 不记录完整令牌、配对码、证书私钥、管理凭据和完整客户端 IP |

### 6.2 稳定字段

| 字段 | 内容 |
| --- | --- |
| `level` | 日志等级 |
| `time` | 带偏移时间 |
| `message` | 中文事件描述 |
| `component` | `master`、`node`、`storage`、`http` 等组件 |
| `request_id` | 当前进程生成的请求 ID，存在请求上下文时必填 |
| `parent_request_id` | 经格式校验接受的上游关联值，存在时填写 |
| `authorization_id` | 下载授权关联值，后续链路存在时填写 |
| `task_id` | 节点控制或同步任务标识，存在时填写 |
| `node_id` | 节点标识，不使用敏感连接信息代替 |
| `error_code` | 稳定内部错误码；对外文案仍为中文 |

示例事件文案：

```json
{"level":"info","message":"主节点健康服务已启动","component":"master","listen":":8080"}
{"level":"warn","message":"配置字段缺失，已使用默认值","component":"config","field":"logging.retention_days","value":30}
{"level":"error","message":"数据库迁移失败，服务无法就绪","component":"storage","request_id":"...","error_code":"DB_MIGRATION_FAILED"}
```

## 7. 请求 ID 设计

### 7.1 生成与传播

| 链路位置 | 规则 |
| --- | --- |
| 主节点入站 HTTP | 对每个请求生成新的不可预测 ID，不能把客户端提供值作为主键 |
| 上游代理关联 | 若上游 `X-Request-ID` 满足长度和字符格式校验，则保存为 `parent_request_id`；不替代新 ID |
| 主节点响应 | 固定返回 `X-Request-ID: <本次生成 ID>` |
| 挑战和授权 | 后续写入 `challenges.request_id`、`download_authorizations.request_id` |
| 控制任务 | 后续派发节点任务时附带授权或操作的请求 ID，并另有 `task_id` |
| 下载节点入站 | 为实际下载 HTTP 请求生成自身 `node_request_id`，同时从已校验令牌关联主节点授权/请求 ID |
| 流量上报 | 携带节点请求 ID、主节点请求 ID、授权 ID 和节点单调事件序号 |

### 7.2 格式和保护

- 实现方案采用加密安全随机字节生成的不可预测标识，使用无歧义可打印编码；不得使用递增数或仅时间戳。
- 入站父关联字段设定长度上限并只接受安全可打印字符，拒绝将换行或控制字符写入日志。
- 请求 ID 不承担鉴权职责；下载令牌和 mTLS 认证不能被请求 ID 代替。
- 中文错误响应在 M1 的健康/配置相关失败中携带本次 `request_id`；后续 API 沿用同一响应合同。

## 8. 健康端点设计

| 程序 | 端点 | 就绪条件 | 返回内容限制 |
| --- | --- | --- | --- |
| 主节点 | `GET /healthz` | 配置成功加载、日志可用、SQLite 连接和迁移完成 | 中文状态、程序角色、版本、请求 ID；不暴露路径/凭据 |
| 下载节点 | `GET /healthz` | 配置成功加载、日志可用 | 中文状态、程序角色、版本、请求 ID；不得声明已同步或可路由 |

主节点成功响应示意：

```json
{
  "状态": "正常",
  "角色": "主节点",
  "说明": "基础服务已就绪",
  "请求ID": "生成的请求标识"
}
```

该中文 JSON 仅服务 M1 健康检查，不替代 M4 公共页面或正式 API 响应格式设计。

## 9. 构建脚本方案

### 9.1 脚本与产物

| 脚本 | 运行环境 | 产物 |
| --- | --- | --- |
| `scripts/build-windows.bat` | Windows `cmd.exe` | `dist/windows-amd64/mirror-master.exe`、`mirror-node.exe`、`configs/*.example.yaml` |
| `scripts/build-linux-amd64.sh` | Linux shell 或具备 Go 交叉构建环境的 shell | `dist/linux-amd64/mirror-master`、`mirror-node`、`configs/*.example.yaml` |

### 9.2 构建行为

1. 脚本使用 UTF-8 执行/输出策略，Windows 脚本开头明确切换 UTF-8 代码页并在中文失败信息中返回非零退出码。
2. 构建固定执行两个入口：`./cmd/master` 和 `./cmd/node`。
3. 产物目录仅存二进制及带中文注释的配置示例；不得把真实凭据、数据库或日志打包。
4. 版本、提交号和构建时间通过只读构建变量注入，健康响应可以展示非敏感版本信息。
5. 脚本运行前执行行数门禁与 `go test ./...`；任一失败终止构建。
6. Linux 脚本设置 `GOOS=linux`、`GOARCH=amd64`；Windows 脚本设置对应 Windows amd64 目标，具体是否启用 `CGO` 由 SQLite 驱动选择在实现确认时固定。

### 9.3 UTF-8 和行数门禁

- `scripts/check-file-lines.ps1` 检查 `.go`、后续 `web/` 资源、脚本及非 Markdown 维护文本的行数；`docs/*.md` 明确排除。
- 对超过 250 行的文件，构建默认失败；若存在确有必要的例外，必须在设计/变更文档中说明职责无法合理拆分的原因并显式列入允许清单。
- 测试读取所有示例 YAML 并校验中文注释在 UTF-8 下可正确解析和展示。
