## 1. 文档定位

M1 已完成实现，本文件不要求为文档顺序重写有效代码。本文件从现有代码和迁移追认数据事实，并成为后续数据结构、迁移和关键事务变化的专门合同。

| 结论类型 | 含义 |
| --- | --- |
| 已实现 | 当前迁移或配置代码已经存在，启动时可创建或校验 |
| 已预留未启用 | 表或字段已存在，但对应业务尚未运行 |
| M2 预计新增 | 只有在本文件及 M2 相关合同确认后才可新增迁移或代码 |
| 后续阶段合同 | 为 M3 至 M5 保留的规则，不代表当前服务能力 |

## 2. M1 SQLite 运行机制事实

### 2.1 连接与迁移

| 项目 | 已实现事实 | 与需求一致性 |
| --- | --- | --- |
| 数据库驱动 | 主节点和下载节点均使用 SQLite，驱动为 `modernc.org/sqlite` | 一致 |
| 主节点路径 | 来自 `database.path`，默认 `data/master.db` | 一致 |
| 下载节点路径 | 来自 `storage.state_db`，默认 `data/node-state.db` | 一致 |
| 外键 | 打开连接时执行 `PRAGMA foreign_keys = ON` | 一致 |
| 繁忙等待 | 主节点读取 `database.busy_timeout`，默认 `5s`；下载节点固定 `5s` | 一致 |
| WAL | 主节点由 `database.wal` 控制，默认开启；下载节点开启 | 一致 |
| 并发连接 | 当前连接池 `SetMaxOpenConns(1)` | 适合作为 M1 保守串行基础，后续性能验收再评估 |
| 迁移执行 | 内嵌 SQL，按文件名排序，在单个事务中逐项执行并写 `schema_migrations` | 一致 |
| 时间写入 | 迁移记录使用 UTC RFC3339Nano 时间文本 | 与 UTC 存储合同一致 |

## 3. 主节点现有数据结构逐项核对

### 3.1 核心、项目与资产表

| 表 | 当前关键字段/约束 | 当前可用程度 | 基线核对 |
| --- | --- | --- | --- |
| `schema_migrations` | `version` 主键、`applied_at` | 已用于迁移幂等 | 一致 |
| `runtime_kv` | `key` 主键、`value`、`updated_at` | 已创建，尚无业务写入 | 合理预留 |
| `projects` | 项目标识、公开仓库字段、保留数、预发布开关、倍率、配置摘要 | 已创建，M3 才投影配置 | 字段支持定稿合同；未实现扫描 |
| `releases` | 项目外键、GitHub Release ID 项目内唯一、预发布及选择状态 | 已创建，M3 才写入 | 支持正式/预发布预留 |
| `assets` | Release 外键、GitHub Asset ID 唯一、文件信息、`digest_sha256`、服务状态 | 已创建，M3 才写入 | 支持摘要合同；SQL 本身未强制 `sha256:` 格式，M3 必须在业务写入前严格校验 |

不得误读：

- `projects`、`releases`、`assets` 存在不表示 GitHub 扫描已实现。
- `assets.digest_sha256` 字段存在不表示摘要已经来源可信或校验完成；缺失或非 `sha256:` 的源站摘要在 M3 必须拒绝入可服务流程。

### 3.2 节点与库存表

| 表 | 当前关键字段/约束 | 当前可用程度 | 基线核对 |
| --- | --- | --- | --- |
| `nodes` | `id`、公开名称、单个证书指纹字段、状态、目标带宽、最后心跳、最大镜像项目数、项目分配模式、`routing_ready DEFAULT 0` | 已创建，M2 才运行节点业务 | `routing_ready=0` 可保障新节点不提前路由 |

| `target_inventory` | `(node_id, asset_id)` 主键、期望状态 | 已创建，M3 才形成目标库存 | 支持按节点项目分配生成目标副本 |
| `node_inventory` | `(node_id, asset_id)` 主键、本地摘要、大小、验证时间、状态 | 已创建，M3 才写入校验结果 | 支持最终对账预留 |
| `node_project_assignments` | `(node_id, project_id)` 主键、分配模式、是否分配、热度分数、防抖时间 | 已创建，M3 同步目标使用 | 约束单节点最大镜像项目数 |

M2 强制边界：

- M2 新建或更新的节点不得把 `routing_ready` 置为 `1`。
- M2 库存上报只记录报告合同，不得将 `node_inventory.state` 写为已校验可服务。
- `在线可路由` 只能由 M3 完整库存对账完成后的后续逻辑产生。

## 5. 配置实现事实与差异

### 5.1 已存在的 M2 相关配置形状

| 配置键 | 当前实现事实 | M2 使用边界 |
| --- | --- | --- |
| `server.management_listen` | 默认 `127.0.0.1:9080`，可显式改为管理网络监听 | 管理面板唯一监听入口 |
| `server.control_listen` | 示例 `:9443`，证书齐备时启动 TLS 1.3 控制端口 | 只接受节点 mTLS 的控制消息 |
| `server.enrollment_listen` | 示例 `:9444`，证书齐备时启动 TLS 1.3 登记端口 | 仅服务端证书认证，用于节点首次登记和证书领取 |

| `node.pairing_code_ttl` | 默认 `5m` | M2 配对码过期时间 |
| 主节点 `node.tls.ca_file/ca_key_file/cert_file/key_file` | 已启用：`ca_file/ca_key_file` 是控制/登记服务端 CA，`cert_file/key_file` 用于控制与登记端口服务端证书，`ca_file` 随登记响应下发给节点 | 控制/登记通道必须加载有效 TLS 材料，CA 私钥不得分发给下载节点 |
| 主节点 `node.tls.client_ca_file/signing_ca_*` | 已启用：`client_ca_file` 验证控制通道节点证书，`signing_ca_*` 签发已审批节点证书 | 私钥只作为本地安全材料，不入库、不写日志 |
| `admin.tls.cert_file/key_file` | 已启用：管理面板 HTTPS 服务端证书路径 | Web 管理面板传输保护 |
| `admin.web.users_file` | 管理面板用户哈希文件 | 不保存明文密码 |
| `admin.web.session_secret_file` | 管理面板会话签名密钥文件 | 不写入日志或页面 |
| `admin.web.login_failure_*` | 登录失败窗口、阈值和封禁时长 | 驱动 `admin_ip_blocks` 防爆破 |
| 节点 `master.control_address` | 必须为 HTTPS 地址 | M2 主动拨号控制端口 |
| 节点 `pairing.credential_file`、`tls.*` | 示例已预留路径 | M2 安全落盘身份材料 |

### 5.2 M2 预计最小配置增量

下列配置仍需后续合同确认后加入：

| 预计新增字段 | 原因 | 最小变更策略 |
| --- | --- | --- |
| `node.heartbeat_interval` | 需要明确上报频率并小于现有超时 | 新增正持续时间校验 |

## 6. M1 与需求定稿的偏差检查

| 检查项 | 现状判断 | 影响 | 处置 |
| --- | --- | --- | --- |
| SQLite 与事务迁移基础 | 符合 | 无 | 继续以新增迁移扩展 |
| 新节点默认不可路由 | `routing_ready DEFAULT 0` 符合 | 无 | M2 测试强制保持为零 |
| 配对码不存明文 | 已有字段为 `code_hash`，符合预留 | 无 | M2 实现消费/撤销事务 |
| 证书轮换身份历史 | 现有仅单指纹字段，不足以实现轮换和吊销 | M2 无法仅靠 `nodes` 表安全验证历史证书 | M2 新增 `node_certificates` 表，不重写已有表 |
| 登记审批状态 | 现有无登记请求表 | 无法保存 CSR 审批与领取状态 | M2 新增 `node_enrollment_requests` |
| 会话防重放 | 现有无活动会话/最后确认序号表 | 无法跨重连持久判断控制消息重放 | M2 新增 `node_control_sessions` 与节点本地控制状态 |
| 库存/压力报告骨架 | 心跳仅容纳摘要压力，无库存修订报告表 | 无法单独接收库存报告合同 | M2 新增报告元数据表，不写正式库存 |
| 管理高风险身份审计 | 审计表无管理员证书摘要字段 | 无法记录叠加 mTLS 的安全主体 | M2 扩展审计字段或新增审计扩展表 |
| `assets.digest_sha256` 数据库约束 | SQL 未限定格式 | 若 M3 忽略业务校验会破坏摘要规则 | M3 写入服务严格校验；可在 M3 迁移补 CHECK/导入保护 |

以上均未表明已投入运行的 M1 行为违反需求。差异集中于后续阶段尚未实现所需结构，采用增量迁移即可处理，不需要回退 M1 有效代码。

## 8. 关键事务合同

### 8.1 M2 必须实现的事务

| 事务 | 原子操作 | 失败结果 |
| --- | --- | --- |
| 创建配对码 | 写入仅含安全哈希的配对记录、请求 ID 和到期时间；返回明文只发生在响应内 | 不产生可使用记录 |
| 消费配对码并登记 | 校验未用/未撤销/未过期，标记消费，创建唯一登记请求 | 同一码不得出现两个待审批记录 |
| 批准登记并签证 | 校验登记状态，创建节点和证书身份，写审计；节点 `routing_ready=0` | 不签出孤立证书，不生成可路由节点 |
| 禁用节点 | 更新管理状态及 `routing_ready=0`，使活动证书/会话被拒绝或关闭，写审计 | 不能留下继续接受控制消息的禁用节点 |
| 轮换证书 | 建立新证书记录、使旧证书失效、写审计并触发旧会话结束 | 不能同时保留两个活动身份而无记录 |
| 接收心跳/报告 | 校验证书映射和消息序号，保存报告或心跳并推进确认序号 | 重放不得重复产生状态副作用 |
| 离线判定 | 比较最后心跳和阈值，更新离线与 `routing_ready=0` | 重复执行幂等 |

### 8.2 后续阶段事务合同，尚未实现

| 阶段 | 合同 |
| --- | --- |
| M3 | 只有 GitHub 提供且格式为 `sha256:` 的摘要可进入目标库存；节点最终对账后才允许修改可路由资格 |
| M4/M5 | 签发授权、按倍率扣请求桶、预留实际流量预算必须在同一主节点事务中完成 |
| M5 | 首条正字节流量事件仅首次增加“开始传输授权数”；所有流量只按真实发送字节计入 |

## 9. 不变量与验收

| 不变量 | 验收方法 |
| --- | --- |
| M1 已应用迁移不被重写 | M1 数据库升级 M2 时仅出现新增迁移版本 |

## 10. M3 Release 扫描与同步合同

M2 控制面完成后，M3 已开始正式写入 M1 预留的项目、Release、资产、目标库存和节点库存表，并新增扫描运行状态及节点本地同步任务表。M3 仍不得启用 M4/M5 的公共下载、额度、流量或 SLA 统计。

### 10.1 `projects`、`releases`、`assets`

| 表 | M3 写入语义 | 事务要求 |
| --- | --- | --- |
| `projects` | 从 `projects.yaml` 投影启用状态、公开仓库、保留版本数、预发布开关、倍率和配置摘要 | 单项目扫描事务内 upsert；配置非法时不写半成品 |
| `releases` | 保存 GitHub Release ID、tag、预发布标记、发布时间和是否位于当前保留窗口 | 同项目同 GitHub Release ID 幂等更新 |
| `assets` | 只保存已通过可信 `sha256:` 摘要门禁的候选资产 | `digest_sha256` 必须由业务层严格校验为 `sha256:<64 hex>` 并规范化后写入 |

GitHub asset 摘要只信任 GitHub Release Assets API 响应中的 `digest` 字段。缺失、非 `sha256:`、长度不符或含非十六进制字符的 asset 不得进入 `assets` 可服务候选状态，也不得生成目标库存。

同一项目内允许上游反复使用同一个 Release tag（例如 `latest`）。对外公开的 `/{project_id}/{version}/{file_name}` 路径必须保持唯一：`candidate` 表示当前公开路径解析和授权使用的资产，`pending` 表示已通过摘要门禁、正在同步但尚未公开的新资产，`superseded` 表示不再公开但仍可参与同路径回退判断的旧资产，`removed` 表示当前扫描中已被上游删除或被规则拒绝的资产。若扫描事务发现同一 `tag_name + file_name` 的最新资产尚无可路由 verified 副本，而旧同路径资产仍有可路由 verified 副本，旧资产必须继续保持 `candidate`，新资产标记为 `pending`；待新资产至少在一个节点 verified 后，再把新资产切换为 `candidate` 并把旧同路径资产标记为 `superseded`。若没有任何旧同路径可路由副本，最新资产可直接成为 `candidate`，保持首次发布语义。`removed` 资产不得出现在公开列表、下载路径解析或授权入口中，也不得继续保持 `target_inventory.required`。

### 10.1.1 `project_scan_state`

`project_scan_state` 记录每个项目的自动 Release 扫描调度状态。`project_id` 为主键，`enabled` 和 `config_hash` 来自当前 `projects.yaml` 投影；`last_scan_started_at`、`last_scan_completed_at`、`last_scan_id`、`last_scan_state` 和 `last_error_message` 来自最近一次项目扫描；`next_scan_at` 是自动调度判断是否到期的唯一时间字段。

新增项目或配置摘要变化的启用项目必须把 `next_scan_at` 置为当前时间，以便尽快扫描。禁用或从 `projects.yaml` 移除的项目必须设置 `enabled=0`，不再参与自动扫描，但历史 `sync_scans` 记录保留。

### 10.2 `target_inventory`

`target_inventory` 表示主节点要求某节点最终持有某资产，不表示节点已经持有。

| 字段 | M3 合同 |
| --- | --- |
| `node_id` | 所有已批准且未禁用节点均应有目标库存；离线节点也保留目标 |
| `asset_id` | 必须引用已通过摘要门禁的 `assets` |
| `desired_state` | 至少包含 `required` 与 `remove`，实现可扩展 `held` 等内部状态 |
| `updated_at` | 目标库存重新计算时间 |

同一项目扫描事务中，主节点在写入候选资产、协调重复公开路径后重新计算目标库存并生成缺失或清理任务。`candidate` 和 `pending` 都必须为已分配到该节点的项目生成 `required` 目标库存；公开接口、下载路径解析和授权只使用 `candidate`。事务失败时不得留下资产和目标库存不一致的状态。新节点审批或禁用节点重新启用时，也必须立即按当前节点项目分配补齐该节点目标库存和下载任务，不等待下一次 Release 扫描。

节点项目自动分配按最近 30 天 `daily_project_stats.authorization_count` 排序。`nodes.max_mirror_projects=0` 表示不限制；大于 `0` 时限制该节点 `target_inventory.required` 覆盖的项目数量。自动模式下已分配项目至少保留 3 天，候选项目只有比当前边缘项目高 20% 以上下载量时才替换，避免热度接近项目频繁切换。手动模式由管理面板写入 `node_project_assignments.assigned`，保存时不得超过节点上限。

### 10.3 `node_tasks`

M3 使用 `node_tasks` 记录同步任务状态。

| `task_type` | 语义 |
| --- | --- |
| `asset_download` | 节点下载、校验并落盘指定资产 |
| `asset_delete` | 节点删除已不在目标库存中的本地资产 |
| `inventory_reconcile` | 节点上报完整库存并触发最终对账 |

`asset_download` 首选源仍是 GitHub `assets.source_url`。下载节点可在任务执行前对 GitHub 源站做短期缓存的连通性探测，探测失败时不必对每个文件重复访问 GitHub。主节点可在任务载荷中附带少量 peer fallback 源，来源仅限其他节点仍处于 `target_inventory.required` 且已经按当前 `assets.digest_sha256` 与 `assets.size_bytes` 验证通过的副本。peer fallback 不新增可信摘要来源，不允许下载节点把自行计算摘要写回为 GitHub 可信摘要；主节点仍只信任扫描阶段写入资产表的 `sha256:` 摘要。若源站不可达且没有可用 peer 副本，任务保持临时失败并进入较长退避重试，不写 verified 库存。

任务状态至少覆盖 `pending`、`sent`、`running`、`succeeded`、`failed`、`retry_wait`、`cancelled`、`obsolete`。任务写入必须携带 `request_id`；日志和管理查询使用 `task_id` 排障。短轮询控制连接下，`sent/running` 任务必须带 `lease_expires_at`；节点持续上报 `running` 时主节点只允许续租 `pending/sent/running` 任务，不得把已经进入 `retry_wait`、`failed`、`succeeded`、`obsolete` 或 `cancelled` 的任务回退为 `running`。节点在产生任何终态同步结果并写入待上报队列时，必须同步更新本地 `local_sync_tasks`，确保该任务不会继续被 running ACK 扫描到。只有租约过期后才允许重新派发仍处于可执行队列的任务，避免大文件下载过程中被重复下发。

### 10.4 `node_inventory`

`node_inventory` 表示主节点已接受的节点本地校验结果。写入或更新为已验证状态前必须同时满足：

1. 报告来自已认证 mTLS 控制通道。
2. 资产存在且当前摘要来自 GitHub 可信 `sha256:`。
3. 节点上报摘要等于 `assets.digest_sha256`。
4. 节点上报大小等于 `assets.size_bytes`。
5. 节点未禁用。

摘要或大小不一致、节点明确报告 `missing`/`mismatch`，或完整库存报告未包含某个 `target_inventory.required` 资产时，主节点必须记录不可用状态并立即重新生成 `asset_download` 任务；不得把该副本用于最终对账。

### 10.5 `nodes.routing_ready`

M3 是首个允许把 `routing_ready` 置为 `1` 的阶段，但只能在最终对账通过后执行。必须满足：

- 节点未禁用且心跳未超时。
- 当前控制身份有效。
- 该节点所有 `target_inventory.required` 资产均有匹配的已验证 `node_inventory`。
- 没有运行中、失败未处理或等待重试的必需资产任务。
- 最近完整库存报告晚于目标库存最后更新时间。

任一条件失效时，`routing_ready` 必须回到 `0`。M3 的 `routing_ready=1` 只表示同步库存就绪，不代表 M4 公共下载链路已经可用。

### 10.6 下载节点 `local_assets`

下载节点 M3 写入 `local_assets` 只表示本地文件曾按任务摘要和大小校验并完成原子落盘。每次完整库存上报前，节点必须重新检查 `local_assets.relative_path` 指向的磁盘文件；文件不存在时报告 `missing`，大小或 SHA-256 与本地记录不一致时报告 `mismatch`，恢复一致后报告 `verified`。节点不得以自行计算出的摘要创建主节点未知资产；主节点未下发的本地文件只可作为未知或待清理库存报告。同一相对路径被新资产覆盖时，旧 `asset_id` 的本地库存必须标记为 `superseded` 或不可服务状态；公共可读路径下载必须同时匹配令牌中的 `asset_id` 和本地相对路径。

节点间复制入口只服务 `local_assets.state='verified'` 的本地文件，并要求主节点签发的短期 `replication.v1` 令牌。复制流量属于同步面内部流量，不写入 `download_authorizations`、`pending_traffic_events`、`traffic_events` 或 `daily_*` 用户下载统计；如果 peer 返回的文件不符合任务摘要或大小，接收节点必须丢弃临时文件并按同步任务失败上报。

### 10.7 M3 新增运行表

| 表 | 用途 |
| --- | --- |
| `sync_scans` | 记录周期或手动 Release 扫描的任务 ID、项目、状态、接受/拒绝资产数、错误摘要、请求 ID 和完成时间 |
| `project_scan_state` | 记录每个项目上次扫描、下次扫描和配置摘要，用于分散自动扫描 |
| `local_sync_tasks` | 下载节点本地记录同步任务状态、错误摘要和更新时间，支持断线后排障 |

未来任何表、字段、索引或事务语义变化，必须先更新本文件。

## 11. M4 公共下载链路合同

M4 打通网页 ALTCHA、公开 API PoW、节点绑定令牌和下载节点 Range 文件服务。挑战运行态保存在主节点内存并定期清理，不写入 M1 预留的 `challenges` 表；下载授权仍写入 `download_authorizations`。M4 不启用 M5 的额度扣减、流量预留结算、真实流量入账、统计聚合或 SLA。

### 11.1 `challenges`

| 字段语义 | M4 合同 |
| --- | --- |
| `kind` | 只能为 `altcha` 或 `api_pow`；网页端使用 `altcha`，公开 API 使用 `api_pow` |
| `asset_id` | 挑战绑定的下载意图，提交时必须一致 |
| `client_prefix` | 创建挑战时解析出的客户端 IP 前缀，用于额度、黑名单和排障归因；提交挑战时不再要求当前请求来源前缀一致 |
| `nonce` | 服务端随机挑战材料或其安全表示，不记录可绕过挑战的密钥 |
| `difficulty` | `altcha` 使用 `altcha.difficulty`，默认 `22`；`api_pow` 使用前导零位数，默认 `23` |
| `expires_at` | 短时有效；过期挑战不得消费 |
| `consumed_at` | 成功提交时在同一事务内写入，防止重放 |

ALTCHA 参数不得写入或解释为 API PoW 前导零位数；API PoW 不得复用 ALTCHA challenge 载荷。

### 11.2 `download_authorizations`

M4 可在授权成功时写入 `download_authorizations`，作为签发令牌和排障依据。该写入不代表 M5 的下载授权次数统计已经启用。

| 字段语义 | M4 合同 |
| --- | --- |
| `id` | 授权 ID，必须进入下载令牌声明 |
| `asset_id` | 绑定单个资产 |
| `node_id` | 绑定单个下载节点 |
| `client_prefix_key` | 签发授权时记录的客户端 IP 前缀规范化键，用于额度、流量和排障归因 |
| `expires_at` | 令牌有效期截止 |
| `max_bytes` | 该授权允许发送的最大字节数 |
| `range_limit` | 同一授权允许并发 Range 请求数 |
| `request_id` | 主节点签发请求 ID |
| `first_transfer_at` | M4 不更新；M5 再用于“开始传输授权数” |

### 11.3 授权事务

M4 授权事务必须原子完成：

1. 校验挑战未过期、未消费且资产绑定一致。
2. 选择未禁用、未离线、有公网下载地址，且 `node_inventory` 已验证持有该资产、摘要/大小匹配、`verified_at` 不早于节点最近心跳时间的节点。
3. 写入授权记录并生成签名令牌。
4. 标记挑战已消费。

M4 可调用额度/流量预留接口形状，但这些接口必须为空操作或明确返回未启用；不得扣减 `quota_buckets`，不得写入有效 `traffic_reservations`，不得聚合 `daily_*` 统计。

### 11.4 下载节点数据

下载节点 M4 只可服务 `local_assets` 中状态为已验证、摘要和大小与主节点令牌资产一致且本地文件存在的资产。节点不得因为用户请求缺失文件而回源 GitHub 下载，也不得把本地未知文件暴露为公共下载。

`pending_traffic_events` 在 M4 仍不启用真实流量补报；M5 开始前必须先补充流量事件、幂等确认和断线恢复合同。当前下载令牌使用 Ed25519 非对称签名，主节点保存 `download_token.signing_private_key_file`，下载节点只保存 `download_token.verify_public_key_file`，私钥不得入库或写入日志。

### 11.5 M4 不变量

| 不变量 | 验收方法 |
| --- | --- |
| 网页挑战只使用 ALTCHA | 测试网页接口不接受 API PoW nonce |
| API 挑战只使用 SHA-256 前导零 PoW | 测试默认 `23` 位前导零和规范字符串 |
| 授权只选择最近心跳后可路由且已验证持有资产的节点 | SQLite 事务测试覆盖缺失、副本不一致、`routing_ready=false` 单文件可用和重连旧库存不可用 |
| 下载令牌绑定资产、节点、客户端前缀、有效期、最大字节、Range 并发和请求 ID | 令牌声明测试和伪造/跨节点/跨资产复用测试 |
| M4 不产生 M5 统计 | 测试授权和下载后 `daily_*`、`traffic_events`、`first_transfer_at` 不被作为统计写入 |

## 12. M5 额度统计合同

M5 开始前，本节将 M1 已预留、M4 已写入的授权数据升级为真实额度和统计合同。确认前不得新增或修改 Go 源码、SQL、配置样例或脚本。

### 12.1 请求额度数据

`quota_buckets` 按 `(scope_kind, scope_key)` 保存请求桶余额。M5 必须支持四类作用域：

| `scope_kind` | `scope_key` | 默认容量 |
| --- | --- | --- |
| `ipv4_32` | IPv4 `/32` 规范键 | `120` |
| `ipv4_24` | IPv4 `/24` 规范键 | `600` |
| `ipv6_128` | IPv6 `/128` 规范键 | `120` |
| `ipv6_64` | IPv6 `/64` 规范键 | `600` |

项目下载倍率只扣请求额度。倍率 `3` 表示一次授权同时从地址级桶和网段级桶扣 `3` 个请求令牌；不得把倍率用于 `traffic_reservations`、`traffic_events`、`daily_traffic_stats` 或 `daily_project_stats.sent_bytes`。

### 12.2 授权事务

M5 授权事务必须在单个主节点数据库事务中原子完成：

1. 校验并消费挑战。
2. 选择可路由且已验证持有资产的节点。
3. 补充并扣减地址级和网段级请求额度。
4. 检查并写入地址级和网段级每日流量预算预留。
5. 写入 `download_authorizations`。
6. 增加项目当日 `authorization_count`。

任一步失败必须整体回滚。不得出现扣了请求桶但未签发令牌、签发令牌但无预留、挑战已消费但无授权的中间状态。

### 12.3 流量预留和事件入账

`traffic_reservations` 以授权 ID 为主键，保存同一统计日内地址级和网段级预算预留、地址/网段作用域键及已结算字节。统计日按配置时区计算，默认 `Asia/Shanghai`。

`traffic_events` 继续以 `(node_id, event_sequence)` 为幂等主键。主节点处理首次事件时必须校验节点身份、授权 ID、节点绑定、资产关联、主节点授权请求 ID 和节点请求 ID。重复事件内容一致时只返回确认，不重复聚合；重复事件内容不一致时记录安全告警并拒绝覆盖。

### 12.4 开始传输统计

`download_authorizations.first_transfer_at` 是开始传输授权数的唯一去重依据。主节点收到某授权第一条 `sent_bytes > 0` 的有效流量事件时，在同一入账事务中设置该字段并把 `daily_project_stats.transfer_started_count` 增加 `1`。零字节事件、重复事件和失败请求不得增加开始传输授权数。

### 12.5 每日、累计和项目聚合

| 表 | M5 口径 |
| --- | --- |
| `daily_traffic_stats` | 按统计日、地址/网段等作用域汇总真实发送字节 |
| `daily_project_stats.authorization_count` | 主节点成功签发下载令牌次数 |
| `daily_project_stats.transfer_started_count` | 首次产生正字节响应体的授权数 |
| `daily_project_stats.sent_bytes` | 项目当日真实发送字节 |
| 累计流量 | 所有已幂等入账真实发送字节总和 |

重传、重复 Range 和中途中断前已发送字节均计入真实流量；项目倍率不得放大任何流量字段。

### 12.6 节点 SLA 样本

`node_availability_samples` 由主节点按固定采样窗口写入，不接受节点自报 SLA。`routable=1` 且 `heartbeat_ok=1` 的样本才视为可用样本。公开页面至少展示近 `24h`、`7d`、`30d` SLA，样本不足必须显示“统计样本不足”。

### 12.7 下载节点待确认事件

下载节点 `pending_traffic_events` 必须保存未被主节点确认的流量事件，字段包括单调 `event_sequence`、`authorization_id`、`asset_id`、`node_request_id`、`master_request_id`、`sent_bytes`、`status`、创建时间和确认时间。断线重连后节点补报未确认事件；主节点确认后节点才可标记或清理。

- 下载节点新增 `000004_traffic_events_m5.sql`，未破坏既有本地资产表。
- 授权事务已写入 `quota_buckets`、`traffic_reservations`、`download_authorizations` 和 `daily_project_stats.authorization_count`。
- 主节点流量事件入账已更新 `traffic_events`、`traffic_reservations.settled_bytes`、`daily_traffic_stats`、`daily_project_stats.sent_bytes` 和首次传输计数。
- 控制面实时运行态已瘦身：活动会话、控制消息防重放序号、最近心跳、最近压力报告和最近库存报告摘要保存在主节点进程内存，不再向 `node_heartbeats`、`node_pressure_reports`、`node_inventory_reports` 写高频运行态；`nodes.last_heartbeat_at`、正式库存、任务、授权和流量入账仍按恢复边界写 SQLite。

## 13. M6 加固交付合同

M6 不以重写数据模型为目标。若实现阶段发现必须新增恢复、审计或验收辅助字段，必须先更新本文并新增迁移，不得修改既有迁移文件。

### 13.1 备份和迁移恢复

| 对象 | M6 合同 |
| --- | --- |
| 主节点 SQLite | 升级前备份主库及 WAL/SHM 或完成 checkpoint；备份记录最高迁移版本和 Git 提交 |
| 下载节点 SQLite | 升级前备份 `storage.state_db`，保留未确认流量事件和同步状态 |
| 迁移失败 | 停止服务，保留失败现场，从迁移前备份恢复；不得手工编辑 `schema_migrations` 抢修 |
| 恢复后核验 | 核对 `schema_migrations`、授权、额度桶、流量预留、事件入账、节点身份和未确认补报游标 |

### 13.2 主节点重启恢复

| 数据 | 恢复规则 |
| --- | --- |
| `download_authorizations` | 未过期授权继续可查询；过期或撤销授权不得继续签发新令牌 |
| `quota_buckets` | 从余额和更新时间恢复，不因重启重置为满桶 |
| `traffic_reservations` | 保留预留、结算和统计日；过期未使用预留由清理策略处理 |
| `traffic_events` | 继续以 `(node_id, event_sequence)` 幂等，重复补报不重复入账 |
| `daily_project_stats` | 下载授权次数和开始传输授权数不得因重启重复增加 |
| `node_availability_samples` | 重启期间缺失样本不得按可用计算，公开页面可显示样本不足 |
| 控制面运行态内存 | 最近心跳、压力、库存报告摘要和活动会话可在重启后丢失；节点重连和重新上报后恢复，不得从旧历史表冒充当前样本 |

### 13.3 断线补报和乱序事件

下载节点 `pending_traffic_events` 是断线补报的恢复边界。节点必须在发送前持久化事件，主节点确认后才可标记 `confirmed_at`。

| 场景 | 数据处理 |
| --- | --- |
| 重复事件内容一致 | 返回幂等确认，不更新聚合 |
| 重复事件内容冲突 | 拒绝覆盖，记录安全告警 |
| 事件乱序 | 可写入补报窗口内事件，但确认游标不得越过缺口 |
| 授权已过期 | 已真实发送字节仍入账，后续请求可被拒绝或撤销 |
| 节点本地库丢失 | 必须重新登记或重新同步，不得用未知本地文件恢复公共服务 |

### 13.4 M6 数据验收

M6 最终数据验收至少覆盖：

- 并发授权下请求桶和流量预留不透支。
- Range 重试和多线程下载不重复增加下载授权次数。
- 首条正字节事件只增加一次开始传输授权数。
- 主节点重启后继续接受未确认流量事件补报。
- 迁移失败可从备份恢复到升级前一致状态。
- 故障演练后统计聚合与 `traffic_events` 可核对。
