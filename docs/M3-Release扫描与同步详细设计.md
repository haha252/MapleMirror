## 1. M3 交付边界

M3 只实现 GitHub Release 扫描、可信摘要筛选、目标库存生成、节点同步任务、下载节点本地校验落盘、新节点追平和最终对账。

| 类别 | M3 必须交付 |
| --- | --- |
| 项目扫描 | 主节点按 `projects.yaml` 和 `scan.interval` 扫描公开 GitHub 仓库 Release 列表 |
| Release 选择 | 按项目保留窗口选择正式版；项目启用 `include_prerelease` 时同时选择预发布版 |
| 摘要门禁 | 只有 GitHub 可信响应中格式为 `sha256:<hex>` 的 asset 摘要可进入镜像流程 |
| 目标库存 | 主节点把所有启用项目在保留窗口内可服务候选资产展开为每个节点的目标库存 |
| 同步任务 | 主节点向已配对、未禁用、控制连接有效的节点下发下载或清理任务，并持久记录任务状态 |
| 节点同步 | 下载节点下载到临时文件，计算 SHA-256，校验通过后原子落盘并更新本地库存 |
| 库存上报 | 节点上报本地已校验库存，主节点写入 `node_inventory` 并驱动差异对账 |
| 新节点追平 | 新节点完整持有已校验目标库存并完成最终对账后，才允许 `routing_ready=true` |
| 请求关联 | 扫描、任务、库存、落盘和对账日志均携带请求 ID 或任务 ID，延续 M1/M2 脱敏规则 |

## 2. M3 明确不实现

| 不实现能力 | 所属阶段 | M3 边界 |
| --- | --- | --- |
| 公共下载页面、统计页、关于页、节点状态页 | M4/M5 | M3 不创建公共页面，也不展示可下载入口 |
| 网页 ALTCHA | M4 | 不生成挑战，不校验 ALTCHA，不引入前端组件 |
| 公网 API 与 API PoW | M4 | 不开放项目查询、挑战、授权或路由 API |
| 下载令牌、节点绑定授权、Range 下载 | M4 | 下载节点不对公共用户提供文件传输 |
| 额度扣减、流量预留、流量事件入账 | M5 | 不写请求桶扣减，不结算实际流量 |
| 下载统计、SLA、可用性展示 | M5 | 心跳和库存可用于对账，不产生公开统计结论 |

M3 可以把节点标记为“同步就绪并可供后续路由选择”，但没有公共下载链路，因此 `routing_ready=true` 只表示节点完整持有目标库存，不表示已经有对外下载能力。

## 4. GitHub Release 扫描

### 4.1 扫描范围

主节点只扫描 `projects.yaml` 中 `enabled=true` 的项目，仓库字段必须为 `owner/repo`。M3 只支持公开 GitHub 仓库；私有仓库、任意 Git URL、本地路径和第三方托管源均拒绝。

每个项目扫描以下 GitHub REST API 数据：

| 数据 | 用途 |
| --- | --- |
| Release 列表 | 获取 tag、发布时间、正式/预发布标记、Release ID |
| Release assets | 获取 asset ID、文件名、大小、下载地址、`digest` |
| 条件请求头 | 保存 `ETag`/`Last-Modified`，降低重复扫描开销 |
| 限频响应 | 记录中文告警并按退避时间推迟下次扫描 |

M3 不使用 GitHub Webhook，不要求管理员手动上传 Release 元数据。

### 4.2 调度方式

| 触发 | 规则 |
| --- | --- |
| 启动后首次扫描 | 主节点启动并完成 M2 控制面初始化后，延迟一个很短的随机抖动再执行，避免多实例误启动同时打 GitHub |
| 周期扫描 | 使用 `scan.interval`；值必须为正持续时间 |
| 配置变更后扫描 | M3 不实现热加载；重启后读取新 `projects.yaml` 并扫描 |
| 条件请求 | 同项目保存扫描游标，后续请求携带条件头；`304 Not Modified` 只刷新扫描时间，不重写库存 |
| 限频和退避 | 遇到 `403`/`429` 或 GitHub 限频头时，记录下一次允许扫描时间，不忙重试 |

同一项目同一时间只允许一个扫描任务运行。周期扫描发现上一次仍在执行时，本轮跳过并写中文 `warn` 日志。

### 4.3 手动触发边界

M3 在管理 API 中提供手动扫描入口，但它只面向管理网络、Bearer 管理令牌和管理员 mTLS。手动触发不能绕过以下限制：

- 不能扫描 `projects.yaml` 之外的仓库。
- 不能把禁用项目临时纳入目标库存。
- 不能降低 `sha256:` 摘要校验要求。
- 不能强制选择超过保留窗口的 Release。
- 不能直接把节点置为 `routing_ready=true`。

手动扫描返回的是扫描任务 ID 和中文状态，不同步等待所有下载节点完成资产同步。

### 4.4 错误处理

| 错误 | 处理 |
| --- | --- |
| 项目配置非法 | 拒绝启动或拒绝本轮扫描；中文错误定位到项目 ID |
| GitHub 仓库不可访问或非公开 | 项目本轮扫描失败，保留上一次已确认目标库存，不删除已有可服务资产 |
| GitHub 限频 | 保存退避时间，任务状态为 `deferred`，不重复打满请求 |
| Release 列表解析失败 | 本项目本轮扫描失败，不写入半成品 Release |
| 单个 asset 摘要缺失或不合规 | 拒绝该 asset 进入候选；不影响同 Release 其他合规 asset |
| 数据库事务失败 | 回滚本轮项目扫描写入；任务失败并带请求 ID |

## 5. Release 与资产选择规则

### 5.1 正式版和预发布版

每个项目独立选择 Release：

| 配置 | 选择规则 |
| --- | --- |
| `include_prerelease=false` | 只选择 `prerelease=false` 的正式 Release |
| `include_prerelease=true` | 正式 Release 与预发布 Release 都纳入候选集合 |
| `retain_versions=N` | 在候选集合中按 `published_at` 降序选择最多 N 个 Release |
| Release 草稿 | 不纳入候选 |
| 同发布时间 | 以 GitHub Release ID 或创建顺序作为稳定次序，确保重复扫描结果一致 |

选择结果写入 `releases.selected`。失去保留窗口资格的 Release 不再生成目标库存，但对应文件清理必须等待没有有效任务和后续下载令牌引用；M3 尚无公共下载令牌，清理只需避免删除正在同步中的临时文件。

### 5.2 资产过滤和架构

资产先按文件名应用 `asset_exclude`，再应用 `asset_include`；排除优先。未命中包含规则的资产不进入候选。`architecture_regex` 用于从文件名提取展示架构，提取失败时该资产拒绝进入可服务候选并写中文告警。

资产必须记录：

- GitHub asset ID。
- 文件名。
- 大小。
- 下载 URL。
- 架构。
- 所属项目、Release、tag 和预发布标记。
- 可信 `sha256:` 摘要。

## 6. GitHub asset digest 校验规则

### 6.1 可信来源

M3 只信任 GitHub Release Assets API 响应中的 `digest` 字段。以下来源不得作为进入镜像流程的依据：

- 文件名中的 `.sha256`、`.sig` 或人工约定摘要。
- Release body 或 README 中的摘要文本。
- 下载节点下载后自行计算的摘要。
- 管理员手动传入的摘要。
- 非 GitHub API 的重定向响应头或第三方页面内容。

节点自行计算的 SHA-256 只用于验证“下载内容是否等于 GitHub API 已声明摘要”，不能替代 GitHub 可信摘要。

### 6.2 格式要求

合法摘要必须严格满足：

```text
sha256:<64 位十六进制>
```

规则：

- 算法名前缀必须是 `sha256:`。
- 十六进制长度必须为 64。
- 十六进制大小写可规范化为小写保存。
- 缺失、空字符串、其他算法、长度错误、包含非十六进制字符均拒绝。

拒绝的 asset 不写入 `assets.service_state='candidate'` 或任何可服务状态；可以写扫描告警或拒绝记录，但不得进入 `target_inventory`。

## 7. 主节点目标库存与事务

### 7.1 扫描写入事务

每个项目的扫描结果以事务提交：

1. 投影 `projects.yaml` 到 `projects`，更新 `config_hash` 和配置字段。
2. Upsert 被选择的 `releases`，更新 `selected`。
3. 对每个合规 asset upsert `assets`，保存规范化 `digest_sha256` 和候选状态。
4. 对不再选中的 Release/asset 标记为不可服务或过期候选。
5. 重新计算该项目对所有节点的 `target_inventory`。
6. 为缺失或摘要不一致的节点生成 `node_tasks`。
7. 写入扫描任务状态和请求 ID。

事务失败时不得留下半更新的目标库存。

### 7.2 `target_inventory` 写入语义

`target_inventory` 表示“主节点要求某节点最终持有某资产”的目标，不表示节点已经下载成功。

| 字段 | M3 语义 |
| --- | --- |
| `node_id` | 已批准且未禁用的下载节点 |
| `asset_id` | 通过 GitHub `sha256:` 门禁的候选资产 |
| `desired_state` | `required`、`remove`、`held` 等实现枚举；M3 至少需要 required/remove |
| `updated_at` | 目标库存计算时间 |

目标库存必须覆盖所有符合条件的节点，而不是只覆盖在线节点。离线节点重连后仍按目标库存追平。

### 7.3 `node_inventory` 写入语义

`node_inventory` 表示主节点已接受的节点本地校验结果。只有满足以下条件才可写为可用于最终对账的状态：

1. 资产存在于当前或历史 `assets` 表。
2. 节点上报的摘要等于 `assets.digest_sha256`。
3. 节点上报大小等于 `assets.size_bytes`。
4. 节点状态不是禁用。
5. 报告来自已认证 mTLS 控制通道。

如果节点报告缺失、摘要不一致或大小不一致，主节点将 `node_inventory` 标记为缺失/不一致，并生成重试同步任务；不得将其视为可服务副本。

## 8. 同步任务与状态记录

### 8.1 任务类型

M3 扩展 `node_tasks.task_type`：

| 类型 | 用途 |
| --- | --- |
| `asset_download` | 要求节点下载并校验指定 asset |
| `asset_delete` | 要求节点删除不在目标库存中的本地资产 |
| `inventory_reconcile` | 要求节点上报完整库存并执行最终对账 |

任务状态至少包含 `pending`、`sent`、`running`、`succeeded`、`failed`、`retry_wait`、`cancelled`。

### 8.2 下发规则

主节点只向满足以下条件的节点下发任务：

- 节点已完成 M2 证书身份审批。
- 节点未被管理禁用。
- 当前存在有效 mTLS 控制会话。
- 节点状态允许同步；`routing_ready=false` 不阻止同步。

离线节点的任务保留为 `pending` 或 `retry_wait`，待重连后下发。任务下发消息必须包含 `task_id`、`asset_id`、文件名、大小、下载 URL、`digest_sha256` 和重试策略。

### 8.3 状态与重试

| 情况 | 主节点状态 |
| --- | --- |
| 节点确认收到任务 | `sent` |
| 节点开始下载 | `running` |
| 节点校验并落盘成功 | `succeeded`，等待库存报告确认 |
| GitHub 下载失败 | `retry_wait`，按退避重试 |
| 摘要不匹配 | `failed` 并记录安全告警；可重新生成下载任务但不得接受该文件 |
| 节点磁盘不足 | `retry_wait` 或 `failed`，节点保持不可路由 |
| 目标库存变化 | 旧任务取消或转为清理任务 |

重试次数和退避策略应可配置或采用安全默认值；无限快速重试禁止。

## 9. 下载节点同步执行

### 9.1 下载规则

下载节点接收 `asset_download` 后：

1. 校验任务来自认证控制通道，且任务 ID 未处理或可幂等恢复。
2. 按 `sync.max_workers` 控制并发，按 `sync.bandwidth_limit` 限速。
3. 使用任务中的 GitHub 下载 URL 下载到 `storage.temp_directory`。
4. 临时文件名包含任务 ID，不包含完整令牌、凭据或不可信路径片段。
5. 下载过程中不对公共用户开放该文件。

M3 不要求节点实现公共 Range 下载；节点到 GitHub 的下载可使用普通 HTTP 客户端和必要的重试/断点策略，具体实现以可靠性和测试覆盖为准。

### 9.2 校验与原子落盘

下载完成后：

1. 计算临时文件 SHA-256。
2. 与任务中的 `digest_sha256` 比对。
3. 校验大小等于任务中的 `size_bytes`。
4. 通过后写入 `local_assets`，状态为本地已校验。
5. 使用同一文件系统内的原子 rename 移入 `storage.directory`。
6. 原子落盘成功后删除临时状态并上报任务结果。

校验失败、大小不符、rename 失败或本地状态库写入失败时，不得把文件放入可服务目录；必须清理临时文件或标记为待清理。

### 9.3 清理规则

下载节点只清理主节点明确下发 `asset_delete` 的文件，或清理已失败/过期的临时文件。禁止基于本地目录扫描自行删除未知资产。

清理成功后更新 `local_assets` 并上报库存。清理失败时报告中文错误码，不泄露绝对路径。

## 10. 新节点追平与最终对账

### 10.1 新节点流程

1. M2 配对审批完成后，节点状态为 `syncing` 且 `routing_ready=false`。
2. 节点建立 mTLS 控制连接并上报完整本地库存。
3. 主节点按当前 `target_inventory` 计算缺失和不一致资产。
4. 主节点下发全部缺失下载任务和多余资产清理任务。
5. 同步期间如扫描发现新的目标库存，继续追加差异任务。
6. 节点报告任务完成后，主节点要求一次完整库存上报。
7. 主节点逐项确认目标库存全部由该节点持有且摘要、大小一致。
8. 最终对账通过后，主节点才可把该节点 `routing_ready=true`。

### 10.2 最终对账规则

节点只有同时满足以下条件，才允许 `routing_ready=true`：

- 节点未禁用。
- 节点最近心跳未超时。
- 当前 mTLS 控制身份有效。
- 对该节点的所有 `target_inventory.required` 资产，都有匹配的 `node_inventory.verified`。
- 不存在摘要不一致、大小不一致、失败未重试完成或运行中的下载任务。
- 最近一次完整库存报告的时间晚于目标库存最新更新时间。

任一条件失效时，主节点必须把 `routing_ready=false`。节点重新上线后必须重新执行差异对账，不允许仅凭 M2 心跳恢复路由资格。

## 11. 管理 API 边界

M3 新增或启用的管理能力：

| 接口类别 | 能力 | 安全级别 |
| --- | --- | --- |
| 扫描 | 手动触发全部项目或单项目扫描 | 高风险，要求管理员 mTLS |
| 扫描状态 | 查询最近扫描任务、错误、限频退避 | 普通管理查询 |
| 同步状态 | 查询节点目标库存差异、任务列表和失败原因 | 普通管理查询 |
| 同步控制 | 对单节点触发重新对账或重试失败任务 | 高风险，要求管理员 mTLS |

M3 管理 API 不提供修改 `projects.yaml` 的接口，不提供公共下载地址，不返回 GitHub Token、完整本地路径或节点私钥/证书正文。

## 12. 请求 ID、日志、错误与 UTF-8

- 扫描任务由管理 API 触发时沿用管理请求 ID；周期任务生成内部请求 ID。
- 每个同步任务有 `task_id`，日志同时记录 `request_id`、`task_id`、`node_id`、`asset_id`。
- 中文错误响应和日志应说明“哪个项目/节点/资产失败”，但不得记录 GitHub Token、管理令牌、证书私钥、完整客户端 IP 或本地绝对路径。
- 所有新增源码、配置注释、日志、协议 JSON 和文档继续使用 UTF-8。
- 新增 Go、SQL、脚本、前端资源继续受 250 行限制；Markdown 文档位于 `docs/`，不受该限制。
- Windows 运维读取中文文件示例继续使用 `Get-Content -Encoding UTF8`。
