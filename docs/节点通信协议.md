> **仓库当前协议合同（2026-09-12）：** 新版节点使用 `control.v2` WSS；首次登记使用独立 `/enroll/v2` WSS 短 RPC。`control.v1` raw TLS 在滚动迁移期继续保留，生产全量 v2 稳定后才关闭和删除。本文先定义 v2 正式合同，后半部分保留 v1 legacy 合同供迁移和回归。

> 实现状态：Phase A–G 已完成，并通过本机 3 Node + 公网 HTTPS peer + Chrome 下载 E2E；生产灰度/关闭 v1 listener 属于 rollout gate。

# control.v2 正式合同

## V2.1 连接、TLS 与身份

| 通道 | Master | Node | TLS | 生命周期 |
| --- | --- | --- | --- | --- |
| Enrollment | `server.enrollment_ws_listen`, `/enroll/v2` | `master.enrollment_ws_address` | TLS 1.3，服务端认证 | 短 WSS 文本 JSON RPC |
| Control | `server.control_ws_listen`, `/control/v2` | `master.control_ws_address` | TLS 1.3 + mTLS | 长连接 WSS |
| Public probe | Node 公网 HTTPS endpoint | Master 主动 GET | HTTPS | 数据面可达性验证 |
| Swarm blocks | Node `/internal/swarm/<asset>` | 其他 Node | HTTPS + Master-signed capability | HTTP Range 数据面 |

Control 的节点身份只来自 mTLS `PeerCertificates` 映射，v2 Envelope 不携带 `node_id`。Master 默认直接终止 control mTLS，不信任 `X-Forwarded-Client-Cert` 等普通代理头。每个 node 只允许一个 active v2 session；新会话完成 TLS + `session.hello` 验证后原子接管旧会话，旧 socket 立即关闭且不能继续提交业务消息。

Enrollment 在节点尚无客户端证书时使用 server-auth TLS。节点提交 pairing code、CSR、公钥指纹和 capability；批准后领取证书/CA/下载令牌公钥，然后关闭 enrollment WebSocket，转入 mTLS control。pairing code 文件读取会 trim 首尾空白，非交互 systemd/container 场景可直接完成 enrollment。

## V2.2 WebSocket 与 Envelope

每个 WebSocket text message 恰好承载一个 UTF-8 JSON Envelope；不再使用 v1 的 4-byte 应用层 framing。permessage-deflate 默认关闭，单个逻辑 message hard limit 为 1 MiB；binary frame、malformed JSON、未知 message type 或超限 message 均拒绝。

```json
{
  "v": "control.v2",
  "type": "sync.result",
  "id": "稳定或随机消息标识",
  "reply_to": "被响应消息的 id，可选",
  "sent_at": "2026-09-12T00:00:00Z",
  "payload": {}
}
```

字段规则：

- `v` 固定为 `control.v2`；
- `type` 必须存在于 v2 priority registry；新增 `Type*` 未登记 priority 会使测试失败；
- `id` 必填；需要 durable replay/correlation 的 domain message 使用由业务身份导出的稳定 ID；
- `reply_to` 对响应消息必填，并同时校验业务身份，不能只凭 transport correlation 推进状态；
- v2 不存在 `node_id`、`request_id`、global `sequence`、`accepted_sequence` 或万能 `heartbeat_ack`。

稳定 ID 使用 `control.v2 + message type + length-prefixed domain identity` 的 SHA-256，再编码为 base64url。典型 identity：

- `sync.task` / `sync.result`: `task_id + attempt_id`；
- `download.authorization`: `authorization_id`；
- `traffic.event`: `event_sequence`；
- `authorization.status`: `authorization_id + status + reason + occurred_at`；
- `swarm.manifest.report`: `manifest_id`；
- `swarm.sources.request`: `task_id + attempt_id + asset_id + manifest_id`；
- `inventory.snapshot.segment`: `node_id + revision + segment`。

## V2.3 Reader / Writer / Priority

每个 control session 只有一个 reader 和一个应用层 writer。业务 handler 不直接读取 socket；reader 解码后交给 dispatcher，所有 outbound 业务消息进入 bounded priority queue。transport Ping/Pong/close 不进入业务 queue。

优先级方向固定为 `1 = 最高，128 = 最低`，`0` 保留给 transport fast path。当前 registry：

| Priority | Message |
| ---: | --- |
| 1 | `session.hello`, `session.welcome` |
| 2 | `protocol.error` |
| 4 | `sync.cancel` |
| 8–12 | `sync.result`, `sync.result.ack`, `sync.accepted`, `sync.rejected`, `sync.task` |
| 16–25 | download authorization / authorization status / traffic event 及 ACK |
| 28–29 | public probe challenge / ready |
| 33–40 | Swarm manifest / sources / availability |
| 60–61 | inventory snapshot segment / ACK |
| 76 | `node.status` |

Queue 同时限制 message count 和 bytes；只有 registry 标记为 coalescible 的状态类消息可按 domain key 折叠到最新值。durable 消息队列满时不得静默丢弃。连续高优先级 burst 有公平性上限，避免低优先级状态永久饿死。

## V2.4 Session、重连与状态恢复

Node 主动连接 Master，WSS 配置存在时不会因短暂失败自动降级到 v1；按带 jitter 的指数 backoff 重连。重连后依次恢复 durable outbox、inventory snapshot、Swarm availability/source state 和 `node.status`。

`node.status` 是 runtime-first 状态：包括可用 task slots、active task attempts、asset/partial filesystem capacity、目标/实际带宽、public active downloads、Swarm active uploads 与公网 base URL。Master 高频只更新 runtime，DB `last_seen` 节流持久，不在每个 status 上运行完整 task/inventory reconcile。

## V2.5 Task attempt 合同

同步任务由 `(task_id, attempt_id)` 唯一标识一次实际执行：

```text
pending -> sent(attempt) -> running(attempt) -> succeeded / failed / retry_wait / obsolete / cancelled
```

Master 重发尚未 accepted 的任务时必须保持同一 `attempt_id`；真正 retry 才创建新 attempt。Node 在本地持久化 running attempt 后才发送 `sync.accepted`。旧 attempt 的 accepted/result/cancel 不得改变新 attempt。

`sync.result` 是 durable 事件，Node 持久化后重发直到收到匹配 `reply_to + task_id + attempt_id` 的 `sync.result.ack`。accepted ACK 本身不再需要 ACK-of-ACK；若 accepted 丢失，Master 重发相同 task/attempt，Node 幂等重回 accepted。

## V2.6 Inventory snapshot

Inventory 使用完整 snapshot，不维护 delta/gap-repair 协议。触发点为 session connect、显式 force、必要的本地变化和低频 safety snapshot；不再每分钟全量扫描。

一个 snapshot 可拆为最多 1000 items/segment。Node 在开始 snapshot 前先持久化领取新的单调 `revision`，因此 reconnect/process restart 会使用新 revision，不会在旧 revision 下重建不同内容。Master 持久化 `(node_id, revision, segment)` receipt：

- 同 message ID + 同 payload 重放：幂等接受；
- 同 identity 但 payload 不同：协议错误；
- complete segment 成功后 ACK 最后一段的实际 message ID；
- 旧 revision 的 stale report 不回滚较新的完整库存。

## V2.7 Disk capacity

Node 分别采集 `asset_fs` 与 `partial_fs` 的 `available_bytes / total_bytes / reserved_bytes / valid`。采样失败表示 unknown，不能伪装成真实 0。Master 仅用最新状态粗筛；Node 用本地原子 reservation 做最终 admission。跨文件系统 commit 必须考虑 partial 仍占空间时 asset filesystem 还需容纳完整文件。

## V2.8 Swarm / Manifest

Swarm 使用两层：`piece` 是 hash/availability/share 单位，`block` 是 HTTP Range 传输单位。piece size 为 2 的幂，目标约 1024 pieces，首版 1 MiB minimum、64 MiB auto maximum，协议 maximum 128 MiB、`piece_count <= 8192`；block 固定 2 MiB。超过协议 layout 能力的超大资产回退 whole-file。

Master 从权威 source metadata 获得 whole-file size + SHA-256，不下载资产本体。首个 bootstrap seed 从 origin 流式下载时同时计算 whole SHA-256 和 piece SHA-256；whole digest 未匹配前 piece hashes 不具 authoritative/shareable 资格。whole 校验成功后 Node 先持久化 Manifest outbox，再上报：

```text
manifest_id / asset_id / asset_size / asset_sha256
piece_layout_version / piece_size / piece_count
piece_hash_algorithm=sha256 / compact piece_hash_blob
```

第一台 whole-verified mTLS Node 的合法 Manifest 可立即 authoritative。后续 whole-verified Node 交叉报告；若同一权威 whole digest 出现不同 Manifest，Master 将 asset 标为 conflict，清理 partial availability、取消正在进行的 partial Swarm attempt，并让后续 attempt 进入 whole-file origin / fully-verified peer 模式。source metadata 的 size/digest 改变会清旧 Manifest 状态。

Node 持久化 partial path + verified bitmap，不按 piece 建 SQLite 行；bitmap 批量写。重启后 bitmap 可恢复，但 piece 首次本地复用/对外 serve 前 lazy rehash，失败立即撤销 availability。`/internal/swarm/<asset>` 只允许 Range 完全位于一个 source 已 verified piece 内；接收端仍按 Manifest 对整 piece hash，全部完成后再做 whole SHA-256 + size 校验和 atomic commit。

Source 选择由目标 Node 本地完成：不同 pieces 可并行从不同 peers/origin 下载，同一 piece 单 worker；基础 rarest-first + per-peer failure backoff，block 失败可换源续传。HTTP Range 响应必须严格匹配 `206 + Content-Range + 精确 body length`。origin 不支持 Range 时可退 whole-origin；origin 失效而 peers 覆盖全部 pieces 时仍可完成。

Swarm peer capability 为 Master-signed、短 TTL、`swarm_piece_read` scope 的 bearer capability，绑定 source/target/asset/manifest/layout。内部 Swarm bytes 不计入最终用户 public traffic accounting。同步入站使用 Node-global limiter；Swarm upload 同时受 global egress 和独立 `swarm_upload_limit` 子上限。

## V2.9 Public probe、授权与 accounting

Public probe 的 challenge/ready 走 WSS，但真正验证仍由 Master 对 Node 公网 HTTPS endpoint 发起 GET，不能用 control 心跳代替公网可达性。

Download authorization 由 Master durable delivery 到 Node；Node 先落本地 DB 再回 ACK。public download traffic event 和 terminal authorization status 都是 durable outbox，只有严格匹配稳定 message ID / `reply_to` / domain identity 的 ACK 才可标记 reported。内部 replication/Swarm endpoint 不写 public traffic event。

## V2.10 滚动迁移

迁移顺序固定为：Master 先双栈 -> Node 逐台配置 WSS -> 后台观察 v1/v2 占比与 probe/inventory/accounting/Swarm -> 全部 v2 稳定后 legacy listener disabled by default -> 再观察稳定窗口 -> 删除 raw TLS v1 framing/listener 和 v1-only sequence/schema。

生产灰度完成前，下面的 `control.v1` 合同仍有效。

# control.v1 Legacy 合同

> 状态：滚动迁移兼容合同；新功能不再扩展 v1。
> 协议版本：`control.v1`
> 需求基线：`docs/开发要求.md` 定稿 v1.0（2026-05-27）
> 设计来源：`docs/M2-控制面详细设计.md`

## 1. 信任边界与连接方向

| 项目 | 规则 |
| --- | --- |
| 拓扑 | 首版只有单一主节点，不设计多主协调 |
| 发起方向 | 下载节点始终主动连接主节点，主节点不主动连接 NAT 后的下载节点 |
| 正常控制 | 配对完成后仅允许 TLS 1.3 + mTLS 控制连接传送心跳、报告及未来任务 |
| 首次领证 | 未持节点证书前，节点只能连接独立 TLS 1.3 登记入口；该连接不是认证控制通道 |
| 节点信任 | 节点必须校验主节点 CA 或已部署的服务端信任材料；首次交互登记可在显示证书指纹并人工确认后进行一次性 TOFU |
| 主节点信任 | 控制连接必须校验节点证书链、用途、有效期和已批准活动身份 |
| 可路由性 | M2 会话成功不表示公共可路由，节点始终保持不可路由 |

## 2. 端口与 TLS 合同

M1 已存在 `server.control_listen` 与节点 `master.control_address` 配置形状。M2 实现时增加独立登记地址，不在控制端口提供单向 TLS 降级。

| 通道 | 主节点配置 | 节点配置 | TLS 认证 | 可发送消息 |
| --- | --- | --- | --- | --- |
| 首次登记 | `server.enrollment_listen`（M2 新增） | `master.enrollment_address`（M2 新增） | TLS 1.3，仅服务端证书认证；节点必须验证服务端 | 登记提交、待审批查询/响应、证书领取、协议错误 |
| 控制连接 | 既有 `server.control_listen` | 既有 `master.control_address` | TLS 1.3 + mTLS | 握手、心跳、库存/压力上报、关闭通知、协议错误 |

TLS 固定规则：

- 主节点和下载节点的 `MinVersion` 与 `MaxVersion` 均固定为 TLS 1.3。
- 控制连接客户端证书必须具有客户端认证用途，且对应主节点活动证书身份记录。
- 证书过期、被撤销、已轮换失效或无法映射到节点时，主节点拒绝控制会话。
- 节点被管理禁用或安全隔离时只停止公开下载路由，控制连接仍可建立并继续接收心跳、库存和压力报告。
- TLS 握手失败不返回敏感诊断载荷，日志仅记录安全错误码、请求 ID 和可安全识别的节点/证书摘要。

## 3. 传输帧与消息信封

### 3.1 帧格式

每条消息为一个独立帧：

| 段 | 长度 | 内容 |
| --- | --- | --- |
| 长度头 | 4 字节 | 无符号网络序整数，仅表示随后 JSON 字节长度 |
| 消息体 | 长度头指定 | UTF-8 JSON 对象 |

实现前应在协议常量中固定最大帧长度。M2 最低要求：

- 心跳和压力消息必须使用小尺寸上限。
- 库存报告限制单帧条目数量与总字节，过大报告必须拒绝或未来分批扩展，不允许无限分配内存。
- JSON 解析失败、超长帧或无效 UTF-8 均返回安全协议错误或直接断开连接。

### 3.2 通用信封

```json
{
  "protocol_version": "control.v1",
  "message_id": "消息唯一标识",
  "message_type": "heartbeat",
  "sent_at": "2026-05-28T02:00:00Z",
  "node_id": "节点标识",
  "request_id": "主节点会话关联标识",
  "reply_to": "",
  "sequence": 3,
  "payload": {}
}
```

| 字段 | 类型 | 必填 | 校验规则 |
| --- | --- | --- | --- |
| `protocol_version` | 字符串 | 是 | M2 只接受 `control.v1` |
| `message_id` | 字符串 | 是 | 生成方式不可预测；会话内不得重复 |
| `message_type` | 字符串 | 是 | 必须是当前通道允许的类型 |
| `sent_at` | RFC3339Nano UTC 字符串 | 是 | 仅用于排障和时钟告警，不单独作为防重放依据 |
| `node_id` | 字符串 | 控制连接是 | 必须等于 mTLS 证书映射节点；登记入口为空 |
| `request_id` | 字符串 | 是 | 登记由服务端生成关联；控制消息使用 `welcome` 下发的会话请求 ID |
| `reply_to` | 字符串 | 响应是 | 指向被响应的 `message_id` |
| `sequence` | 非负整数 | 节点控制上行是 | 节点持久递增；登记消息不使用控制序号 |
| `payload` | 对象 | 是 | 按消息类型验证字段 |

## 4. 首次登记与配对流程

### 4.1 配对前置条件

1. 管理员已通过管理面板或主节点本地控制台创建一次性短时配对码。
2. 节点已获得主节点登记入口地址；首次交互模式可显示登记入口 TLS 指纹并要求人工确认。
3. 节点在本地生成密钥对与 CSR；节点私钥不得离开节点，也不得进入日志。

### 4.2 `enroll_request`

节点到登记入口：

```json
{
  "protocol_version": "control.v1",
  "message_id": "登记消息标识",
  "message_type": "enroll_request",
  "sent_at": "2026-05-28T02:00:00Z",
  "node_id": "",
  "request_id": "节点本地关联标识",
  "reply_to": "",
  "sequence": 0,
  "payload": {
    "pairing_code": "一次性配对码",
    "public_name": "华东下载节点",
    "csr_pem": "PEM 编码证书请求",
    "public_key_fingerprint": "sha256:十六进制指纹",
    "capabilities": ["heartbeat.v1", "inventory.report.v1", "pressure.report.v1"]
  }
}
```

| 字段 | 处理规则 |
| --- | --- |
| `pairing_code` | 只用于该请求的安全校验，接收后不得写入普通日志或明文数据库 |
| `public_name` | 中文可显示节点名称；审批时展示 |
| `csr_pem` | 只含公钥及签发请求；服务端验证格式、公钥类型和指纹对应关系 |
| `public_key_fingerprint` | 管理员审批核对使用，不等于已批准节点证书身份 |
| `capabilities` | 只声明 M2 报告能力，不可要求未实现的同步/下载能力 |

主节点在一个事务中校验配对码未过期、未撤销、未消费，随后消费该码并建立唯一登记请求。配对码一经有效提交即不因审批拒绝、领取失败或节点私钥丢失而恢复可用。

### 4.3 登记响应

| 消息类型 | 触发 | 载荷关键字段 | 节点行为 |
| --- | --- | --- | --- |
| `enroll_pending` | 登记成功但尚未批准 | `enrollment_id`、`expires_at`、`retry_after_seconds`、中文说明 | 退避后重新查询/领取，不发送控制消息 |
| `enroll_certificate` | 管理员批准且证书可领取 | `enrollment_id`、`node_id`、`certificate_pem`、`ca_chain_pem`、`download_token_public_key_pem`、`not_after` | 原子写入凭据文件、公钥和主节点 CA 后关闭登记连接，以 mTLS 拨号控制入口 |
| `protocol_error` | 登记无效或已结束 | 错误码、中文说明、服务端请求 ID | 不回显配对码；按错误决定停止或重新申请 |

`enroll_certificate` 永远不含节点私钥，也不含下载令牌签发私钥。`download_token_public_key_pem` 仅用于验证 `download.v2` 下载令牌，不能伪造令牌。证书成功领取后，登记入口不接受该节点的心跳或库存/压力消息。

## 5. mTLS 控制会话

### 5.1 会话建立

1. 节点使用本地证书和私钥主动连接 `master.control_address`。
2. 双方完成 TLS 1.3/mTLS 握手，主节点将证书指纹映射为唯一节点 ID。
3. 主节点拒绝已过期/已失效证书、身份不匹配或第二个未处理的异常会话；节点禁用状态不拒绝控制连接。
4. 节点发送 `hello`；主节点通过 `welcome` 确认会话和消息游标。

### 5.2 `hello`

```json
{
  "protocol_version": "control.v1",
  "message_id": "消息标识",
  "message_type": "hello",
  "sent_at": "2026-05-28T02:01:00Z",
  "node_id": "节点标识",
  "request_id": "节点连接关联标识",
  "reply_to": "",
  "sequence": 1,
  "payload": {
    "last_ack_sequence": 0,
    "capabilities": ["heartbeat.v1", "inventory.report.v1", "pressure.report.v1"],
    "software_version": "构建版本"
  }
}
```

### 5.3 `welcome`

```json
{
  "protocol_version": "control.v1",
  "message_id": "消息标识",
  "message_type": "welcome",
  "sent_at": "2026-05-28T02:01:00Z",
  "node_id": "节点标识",
  "request_id": "服务端会话请求标识",
  "reply_to": "hello 的消息标识",
  "sequence": 0,
  "payload": {
    "session_id": "控制会话标识",
    "accepted_sequence": 1,
    "heartbeat_interval_seconds": 15,
    "heartbeat_timeout_seconds": 90,
    "managed_state": "syncing",
    "routing_ready": false
  }
}
```

M2 的 `managed_state` 只可返回同步中、离线恢复中或禁用拒绝等控制状态；`routing_ready` 必须为 `false`。

## 6. 心跳消息

### 6.1 `heartbeat`

```json
{
  "status": "syncing",
  "uptime_seconds": 120,
  "active_downloads": 0,
  "free_bytes": 53687091200,
  "max_mirror_projects": 0,
  "pressure": {
    "target_bandwidth_bps": 104857600,
    "actual_bandwidth_bps": 0,
    "ratio": 0
  },
  "inventory_digest": "",
  "inventory_report_revision": 0
}
```

| 字段 | M2 处理 |
| --- | --- |
| `status` | 只作为节点声明采集；不能把节点变为在线可路由 |
| `uptime_seconds` | 非负数，排障用途 |
| `active_downloads` | 非负数，M2 不生成下载统计 |
| `free_bytes` | 非负数 |
| `max_mirror_projects` | 节点声明自身最多承接的镜像项目数，`0` 表示不限制；主节点持久化后用于目标库存分配 |
| `sync_task_slots_available` | 可选，节点当前可接收的同步任务空槽数；缺省表示旧节点未声明，主节点不得当作已知 `0` |
| `pressure.target_bandwidth_bps` | 与管理配置比对；主节点配置为判断依据 |
| `pressure.actual_bandwidth_bps` | 非负数；节点按非回环网络接口的上行发送字节差值计算，不统计 `127.0.0.1`、`::1` 等本地回环连接，避免 nginx 回源转发被重复计入；首次采样或平台不支持时可为 `0` |
| `pressure.ratio` | 主节点根据实际/目标重新计算后保存 |
| `inventory_*` | 仅指向报告版本，不是库存验证完成证明 |

### 6.2 `heartbeat_ack`

载荷至少包含：

| 字段 | 含义 |
| --- | --- |
| `accepted_sequence` | 已幂等处理的最后节点上行序号 |
| `server_time` | 主节点 UTC 时间 |
| `managed_state` | 当前控制状态 |
| `routing_ready` | M2 固定为 `false` |

节点按服务端下发间隔发送心跳。超过 `node.heartbeat_timeout` 未接到有效心跳时，主节点先记录心跳延迟；继续超过 `node.heartbeat_offline_grace` 且没有活动控制会话时，才标记离线并保持不可路由，关闭或淘汰该控制会话。

## 7. 库存与压力报告骨架

### 7.1 `inventory_report`

```json
{
  "report_id": "报告标识",
  "revision": 1,
  "generated_at": "2026-05-28T02:02:00Z",
  "complete": true,
  "items": []
}
```

库存条目若存在，仅可使用下列字段：

| 字段 | 类型 | M2 含义 |
| --- | --- | --- |
| `asset_id` | 字符串 | 未来 M3 识别资产使用；M2 不据此创建资产 |
| `size_bytes` | 非负整数 | 节点声明值 |
| `digest_sha256` | 字符串 | 提供时须满足 `sha256:` 形式，但 M2 不认定其为 GitHub 可信摘要 |
| `local_state` | 字符串 | M2 只接受报告态，如 `reported`、`missing`；M3 使用 `verified`、`missing`、`mismatch` 参与对账 |

主节点按 `node_id + revision` 幂等保存接收结果。M2 不写入已验证库存，不执行缺失同步，不允许该报告使节点可路由。

### 7.2 `public_probe`

M6 起 `heartbeat_ack` 可携带一次性 `public_probe` 挑战：

```json
{
  "accepted_sequence": 42,
  "server_time": "2026-06-08T12:00:00Z",
  "managed_state": "ready",
  "routing_ready": true,
  "public_probe": {
    "challenge_id": "探测挑战标识",
    "nonce": "主节点随机值",
    "expires_at": "2026-06-08T12:00:20Z",
    "algorithm": "ecdsa-p256-sha256"
  }
}
```

节点收到挑战后，必须先用当前控制证书私钥签名以下 UTF-8 字节串，并在公网文件服务安排好短期响应：

```text
mirror-node-public-probe.v1
node_id
challenge_id
nonce
expires_at
```

安排完成后，节点必须立刻通过控制通道发送 `public_probe_ready`：

```json
{
  "challenge_id": "探测挑战标识"
}
```

主节点只有在收到 `public_probe_ready` 后才开始请求公网探测路径 `GET /.well-known/mirror-node/probes/{challenge_id}`。响应 JSON 包含 `node_id`、`challenge_id`、`nonce`、`expires_at`、`signature`，并必须返回 `Cache-Control: no-store`。主节点使用当前 active 节点证书公钥验签。若节点在挑战过期前未发送 `public_probe_ready`，主节点按网络/控制链路超时累计失败。未 ready、DNS、TCP、TLS 或超时等网络类失败连续达到 `node.public_probe_network_failures` 次后，节点暂停公开下载路由但控制面状态不改为离线；HTTP 2xx 但 JSON、字段或签名错误时单次离线。

### 7.3 `pressure_report`

```json
{
  "report_id": "报告标识",
  "sampled_at": "2026-05-28T02:02:00Z",
  "sample_window_seconds": 10,
  "target_bandwidth_bps": 104857600,
  "actual_bandwidth_bps": 0,
  "pressure_ratio": 0,
  "active_downloads": 0,
  "free_bytes": 53687091200,
  "max_mirror_projects": 0
}
```

M2 校验数值非负、窗口合理，并自行重新计算压力比。`actual_bandwidth_bps` 由节点按采样窗口统计非回环网络接口的上行发送字节差值，Linux 节点使用 `/proc/net/dev` 的发送字节，Windows 节点使用 IP Helper 网卡发送字节计数，都会排除本地回环接口，避免 nginx 在本机回源时重复计算带宽。`max_mirror_projects` 与心跳字段同义，作为心跳外的容量兜底上报。`sync_task_slots_available` 可选，语义与心跳一致；缺省表示未声明，不得当作已知 `0`。报告只作为状态和排障样本，不进入公共下载路由、流量入账或 SLA 统计。

## 8. 序号、幂等与重放防护

| 项目 | 规则 |
| --- | --- |
| 节点上行序号 | `hello` 后的控制消息使用节点持久化单调序号 |
| 主节点确认 | 每个确认响应返回最后接受的上行序号 |
| 重复消息 | 已接受序号的重复发送返回幂等确认，不重复生成报告/状态副作用 |
| 序号跳跃 | 记录中文协议告警；实现时明确可接受窗口，禁止静默跳过安全关键操作 |
| 重连 | 节点发送最后确认游标，主节点以已持久化游标对齐 |
| 会话争用 | 同一节点只保留一个活动 mTLS 会话；替换旧会话必须记录原因 |
| 管理关闭 | 禁用/轮换可发送关闭消息，关闭动作不依赖节点确认才能生效 |

## 9. 状态流转

```mermaid
stateDiagram-v2
    [*] --> "待配对"
    "待配对" --> "同步中": 审批签证并建立身份
    "同步中" --> "离线": 心跳超时或连接中断
    "离线" --> "同步中": 证书有效并重新连接
    "同步中" --> "禁用": 管理员禁用
    "离线" --> "禁用": 管理员禁用
    "禁用" --> "同步中": 管理员启用后重新认证
```

M2 禁止的状态流转：

- 不允许节点自报或心跳触发 `在线可路由`。
- 不允许库存报告触发 `在线可路由`。
- 不允许重新上线直接恢复未来公共授权资格；最终库存对账属于 M3。

## 10. 错误码与断连行为

| 错误码 | 触发 | 行为 |
| --- | --- | --- |
| `PROTOCOL_VERSION_UNSUPPORTED` | 协议版本不支持 | 返回安全错误后关闭 |
| `FRAME_TOO_LARGE` | 帧超出允许长度 | 记录告警并立即关闭 |
| `PAIRING_CODE_INVALID` | 配对码不可验证 | 拒绝登记，不回显凭据 |
| `PAIRING_CODE_EXPIRED` | 配对码过期 | 拒绝登记，要求重新生成 |
| `PAIRING_CODE_CONSUMED` | 配对码已消费 | 拒绝登记，要求重新生成 |
| `ENROLLMENT_PENDING` | 登记仍待审批 | 返回退避时间 |

## 12. M3 同步任务扩展

M3 已在 `control.v1` 上增加同步任务消息，不改变 TLS 1.3 + mTLS 控制连接、信封、序号、幂等和重放防护规则。节点仍主动连接主节点，任务只能从已认证主节点下发。

### 12.1 新增消息

| 消息类型 | 方向 | 用途 |
| --- | --- | --- |
| `sync_task` | 主节点到节点 | 下发资产下载、资产清理或完整库存对账任务 |
| `sync_task_ack` | 节点到主节点 | 确认收到任务，声明是否开始执行 |
| `sync_task_progress` | 节点到主节点 | 报告下载进度、校验进度或清理进度 |
| `sync_task_result` | 节点到主节点 | 报告任务成功、失败、校验不匹配或需重试 |
| `inventory_reconcile_request` | 主节点到节点 | 要求节点上报完整库存，用于最终对账 |
| `inventory_reconcile_result` | 节点到主节点 | 报告完整库存生成结果和报告修订 |

### 12.2 `sync_task` 载荷

```json
{
  "task_id": "同步任务标识",
  "task_type": "asset_download",
  "asset": {
    "asset_id": "资产标识",
    "file_name": "example.zip",
    "size_bytes": 12345,
    "download_url": "https://api.github.com/repos/owner/repo/releases/assets/1",
    "digest_sha256": "sha256:64位十六进制摘要"
  },
  "retry_after_seconds": 0
}
```

| 字段 | 规则 |
| --- | --- |
| `task_id` | 必填，用于节点幂等执行和日志关联 |
| `task_type` | `asset_download`、`asset_delete`、`inventory_reconcile` |
| `asset.digest_sha256` | 必须是主节点已验证的 GitHub `sha256:` 摘要 |
| `download_url` | 仅用于节点向 GitHub 下载源文件；不得包含管理面板凭据或节点私钥 |
| `file_name` | 仅作相对安全文件名输入；节点必须清理路径穿越字符 |

`asset_download` 可携带 `fallback_sources` 数组，用于 GitHub 直连临时失败时从其他下载节点复制文件。每个 fallback 源至少包含源节点 ID、可读节点名、复制下载 URL 和短期一次性 `replication.v1` bearer 令牌。大文件 fallback 可额外携带 `parts` 数组，每个分片包含 `range_start`、`range_end` 和独立短期一次性令牌；源节点必须校验请求 `Range` 与分片令牌绑定范围完全一致。主节点只可选择当前在线、未禁用、具备 `public_download_base_url`，公网探测网络失败未达到 `node.public_probe_network_failures` 阈值，该节点对该资产仍处于 `target_inventory.required`，且 `node_inventory` 已按当前资产摘要和大小验证通过的其他节点；不得把任务接收节点自身作为 fallback 源。

`asset_delete` 用于清理 `target_inventory.remove` 且仍被主节点记录为 verified 的本地副本。主节点派发前必须再次确认目标仍为 `remove` 且 `node_inventory` 仍为 verified；目标重新变为 `required` 或副本已不再 verified 时，未完成删除任务必须归档，不得继续下发。节点收到删除任务后，必须按本地 `local_assets.relative_path` 清理安全相对路径；文件不存在或删除成功后，才可把 `local_assets` 标记为 `removed` 并返回 `succeeded`。删除失败、路径不安全或本地状态更新失败时必须返回 `temporary_error`，不得谎报成功。

主节点通过短轮询控制连接下发同步任务时，会为 `sent/running` 任务设置租约。下载节点收到任务并开始异步执行后，后续控制轮询必须继续以 `sync_task_ack` 上报 `running`，主节点据此续租；`sync_task_ack` 只表达接收和续租语义，`accepted`、空状态和其他非终态兼容值按 `running` 处理，不得用 `failed` 表达接收阶段失败，失败必须通过 `sync_task_result` 进入退避或终态处理。租约未过期的任务不得因新会话建立而重新派发。租约过期表示节点进程可能中断，主节点可把任务恢复为 `pending`。

节点执行顺序必须为：先对 `asset.download_url` 所属 GitHub 源站做短期缓存的连通性探测；探测通过后尝试 GitHub 文件下载，只有 GitHub 探测失败、请求失败、非 2xx 或响应体读取失败时才尝试 `fallback_sources`。探测结果必须在节点本地短期缓存，并合并同一源站的并发探测，避免同一轮同步中每个文件都访问 GitHub。如果 GitHub 已返回完整文件但摘要或大小不匹配，节点不得改用 peer 覆盖该失败。peer 只提供字节流，最终落盘仍必须同时匹配主节点在任务中下发的 `asset.digest_sha256` 与 `asset.size_bytes`。

当 GitHub 源站不可达且任务没有可用 `fallback_sources` 时，节点返回 `temporary_error`。主节点如果此时已经确认其他节点持有该资产 verified 副本，应立即把任务恢复为待派发，使下一次派发携带 peer fallback；否则按更长的临时错误退避重试。该场景不得降级为成功、不得写入 verified 库存，也不得阻塞后续有 peer fallback 的任务使用节点间复制。

`replication.v1` 令牌由主节点签名，至少绑定资产 ID、源节点 ID、目标节点 ID、过期时间、请求 ID 和任务 ID；分片令牌还必须绑定闭区间 `range_start/range_end`。当前复制入口不建立目标节点 mTLS 身份，`target_node_id` 只用于签发审计和任务绑定，令牌本身按短期一次性 bearer 能力处理：下载节点必须通过 `Authorization: Bearer` 请求，源节点不得接受查询参数令牌或重复使用同一令牌，默认有效期不得超过 2 分钟。复制令牌不得用于公网用户下载，不得进入用户额度、Range 并发限制或 M5 流量统计；源节点校验令牌和本地 verified 资产后只返回文件内容。分片复制任一分片失败时，接收节点必须丢弃临时文件并按同步任务失败上报。

### 12.3 任务结果

`sync_task_result` 至少包含：

| 字段 | 含义 |
| --- | --- |
| `task_id` | 对应任务 |
| `asset_id` | 资产任务必填 |
| `result` | `succeeded`、`failed`、`digest_mismatch`、`size_mismatch`、`temporary_error` |
| `local_digest_sha256` | 节点实际计算摘要；失败时可返回，主节点只用于排障和重新同步，不作为可信摘要来源 |
| `size_bytes` | 节点实际文件大小 |
| `message` | 中文摘要，不含绝对路径或凭据 |
| `peer_fallback_attempted` | 可选布尔值；为 `true` 表示本次执行已经实际尝试过节点间复制，主节点不得再因同一批 peer 立即热重试 |

节点只有在下载完成、大小匹配、SHA-256 等于任务摘要且原子落盘成功后，才能对 `asset_download` 返回 `succeeded`。`asset_delete` 只有在本地文件不存在或删除成功且 `local_assets` 已标记 removed 后，才能返回 `succeeded`。任何失败结果都不得使主节点写入已验证 `node_inventory`。

`inventory_reconcile` 的 `succeeded` 结果只表示节点已确认对账任务并将在完整库存中反映实时校验结果，不得直接让主节点把该任务推进到完成状态或恢复 `routing_ready`。主节点只有在后续接受新的 `complete=true` 完整库存报告并执行最终对账后，才可完成对应的 `inventory_reconcile` 任务。

主节点处理资产任务结果时，必须先读取 `node_tasks.asset_id` 作为权威任务资产，并要求节点回包 `asset_id` 非空且完全一致。空 `asset_id` 或与任务不一致的结果不得推进为 `succeeded`，不得写入 verified 库存，也不得按回包资产判断任务是否过期；只能按任务资产进入失败或重试路径。

如果下载任务返回结果时，该资产已因新一轮扫描、重复版本号覆盖或目标库存变化而不再是当前 required candidate，主节点必须把任务归档为 `obsolete`，不得把结果写成 verified 库存。删除任务返回成功时，主节点必须确认目标库存仍为 `remove`，再把对应 `node_inventory` 标记为 `removed`。下载节点本地若以同一个 `project/version/file_name` 覆盖旧资产，应把旧 `asset_id` 的 `local_assets` 行改为不可服务状态。

### 12.4 完整库存报告

M3 继续使用 `inventory_report`，但其条目从 M2 的报告骨架升级为可参与对账的本地库存声明。主节点接受为正式 `node_inventory` 前仍必须校验资产存在、摘要一致、大小一致和节点身份有效。

下载节点发送完整库存报告前必须重新检查 `local_assets` 中记录的磁盘文件。文件存在且大小和 SHA-256 与本地记录一致时上报 `verified`；文件不存在时上报 `missing`；文件存在但大小或 SHA-256 不一致时上报 `mismatch`。`inventory_reconcile` 任务要求节点在下一次完整库存上报中反映该实时校验结果，而不是只确认任务已收到。

主节点接收完整库存报告后，若目标资产被报告为 `missing`/`mismatch`，或某个 `target_inventory.required` 资产未出现在完整报告中，必须将该副本标记为不可用于路由并重新生成 `asset_download` 任务。旧节点上报的空值或 `reported` 可按兼容路径继续通过摘要和大小校验。

主节点必须持久化每个节点最新已接受的完整库存 `revision`。只有大于该边界的新完整报告才可执行缺失标记、修复任务生成和路由就绪对账；重复或更旧的完整 `revision` 只能返回幂等确认，不得重新执行缺失标记或修复任务生成。若该旧 revision 已被持久化接受，主节点可按当前 `target_inventory`、`node_inventory` 和 `node_tasks` 状态重新计算 `routing_ready`，用于恢复重连时被清零的就绪状态。分片库存按同一 `revision` 聚合，只有最终 `complete=true` 帧提升该边界。

最终对账通过前，节点必须保持 `routing_ready=false`。最终对账通过后，主节点可在 `heartbeat_ack` 或后续状态响应中返回 `routing_ready=true`；该值只表示 M3 库存同步就绪，不代表 M4 公共下载服务已启用。

### 12.5 M3 仍禁止的协议行为

- 不下发公共下载令牌。
- 不接收用户 Range 下载请求。
- 不上报真实用户流量事件。
- 不把节点自行计算摘要作为 GitHub 可信摘要。
- 不因单个任务成功直接把节点设为可路由；必须通过完整目标库存最终对账。

在新增消息类型前，必须更新本文、数据模型合同与相应测试，再修改协议代码。

## 13. 公共下载链路扩展

公共下载请求仍由客户端直接访问被绑定的下载节点 HTTP 文件服务。新签发的公共下载令牌是短随机 opaque token；主节点通过 `control.v1` 把授权详情下发到目标节点，节点按本地缓存校验 token 哈希、资产、节点、时限、字节上限和 Range 并发。

### 13.1 下载授权下发与校验

主节点签发授权后发送 `download_authorization`，节点写入本地 `local_authorizations` 后回复 `download_authorization_ack`。授权详情至少绑定：

| 字段 | 规则 |
| --- | --- |
| `authorization_id` | 用于日志和后续状态查询 |
| `token_hash` | 短下载令牌的 SHA-256 哈希，节点不得保存明文 token |
| `asset_id` | 必须与请求资产一致 |
| `node_id` | 必须等于本节点身份 |
| `client_prefix` | 主节点签发时记录的客户端 IP 前缀，用于流量归因和排障；节点不要求它匹配当前请求来源前缀 |
| `expires_at` | 过期即拒绝 |
| `max_bytes` | 限制该授权可发送的最大字节 |
| `range_concurrency_limit` | 限制同一授权并发 Range 请求 |
| `request_id` | 主节点签发请求 ID，节点日志必须关联 |

节点不得接受哈希不存在、跨节点、跨资产、过期或已本地作废的令牌。兼容期内，节点仍可接受旧版 Ed25519 签名令牌。

### 13.2 节点文件服务规则

M4 下载节点只服务本地 `local_assets` 中已校验资产。校验顺序为：令牌签名与声明、资产 ID、本地库存状态、文件存在性、Range 合法性和并发限制。任一失败均返回中文错误和节点请求 ID，不回源下载、不泄露本地路径。

节点必须支持普通完整下载和单段 HTTP Range 断点续传。M4 可以不支持 multipart Range；如不支持，必须返回稳定错误码。

### 13.3 M4 不新增的控制消息

| 消息 | M4 状态 |
| --- | --- |
| 下载令牌下发 | `download_authorization` / `download_authorization_ack` 通过控制通道下发授权详情 |
| 下载撤销广播 | 可预留实现点，M4 可不实现主动撤销广播 |
| 真实流量事件 | 不实现；M5 再定义事件字段、序号、确认和断线补报 |
| SLA 样本 | 不实现；M5 再定义统计事件 |

M4 的节点日志可记录授权 ID、资产 ID、请求 ID、发送结果和完整客户端 IP/前缀，但不得把这些日志解释为 M5 统计入账。

## 14. M5 流量事件扩展

M5 在 `control.v1` 上新增下载流量事件与确认消息。公共下载请求仍不走控制帧；控制通道接收下载节点对已发生传输的真实字节上报。

### 14.1 新增消息

| 消息类型 | 方向 | 用途 |
| --- | --- | --- |
| `traffic_event` | 节点到主节点 | 上报一个下载请求或分段产生的真实发送字节 |
| `traffic_event_ack` | 主节点到节点 | 确认已幂等接收的事件序号 |
| `traffic_replay_request` | 主节点到节点 | 要求节点从指定序号补报未确认事件 |

### 14.2 `traffic_event` 载荷

```json
{
  "event_sequence": 42,
  "authorization_id": "授权标识",
  "asset_id": "资产标识",
  "node_request_id": "节点请求标识",
  "master_request_id": "主节点授权请求标识",
  "sent_bytes": 1048576,
  "range_start": 0,
  "range_end": 1048575,
  "status": "completed",
  "reported_at": "2026-05-28T12:01:00Z"
}
```

| 字段 | 规则 |
| --- | --- |
| `event_sequence` | 节点本地持久化单调递增；主节点以 `(node_id, event_sequence)` 幂等 |
| `authorization_id` | 必须来自主节点下载授权 |
| `asset_id` | 必须与授权绑定资产一致 |
| `node_request_id` | 下载节点处理 HTTP 下载请求时生成 |
| `master_request_id` | 下载授权中的主节点签发请求 ID |
| `sent_bytes` | 本事件真实发送响应体字节，不能用预估值替代 |
| `status` | `partial`、`completed`、`aborted`、`failed` 等 |

节点不得上报未实际写给客户端的字节。零字节事件可用于排障，但不得触发开始传输授权数。

### 14.3 `traffic_event_ack`

```json
{
  "accepted_sequence": 42,
  "duplicate": false,
  "message": "流量事件已入账"
}
```

主节点对重复且内容一致的事件返回幂等确认，不重复聚合。若重复序号内容不一致，主节点返回协议错误并记录中文安全告警。

### 14.4 断线补报

下载节点必须先把事件写入本地 `pending_traffic_events`，再通过控制通道发送。控制连接断开后，节点在重连 `hello` 后按主节点确认游标补报未确认事件。主节点可发送 `traffic_replay_request` 要求从某个序号重新发送，节点不得跳过未确认事件。

如果下载响应已经向客户端写出字节，但本地 `pending_traffic_events` 写入失败，节点必须保留该授权的未落库发送状态。同一授权的后续请求必须先补写这些事件；补写失败时必须拒绝继续发送，不能清空内存预算后按偏小的已入库字节重新放行。

### 14.5 M5 协议不变量

- 流量事件必须携带节点请求 ID、主节点授权请求 ID、授权 ID 和单调事件序号。
- 主节点入账依据是节点真实发送字节，不是资产大小、授权 `max_bytes` 或 HTTP `Content-Length` 预估。
- 节点心跳、压力报告和库存报告不得替代真实流量事件。
- 流量事件日志可记录完整客户端 IP 用于排障，但不得记录完整下载令牌或本地绝对路径。
- 当前实现会在节点控制客户端建立连接后补报本地未确认 `pending_traffic_events`，主节点返回 `traffic_event_ack` 后节点标记确认时间。

## 15. M6 加固交付协议要求

M6 不改变 `control.v1` 的基础信封、TLS 1.3、mTLS 和消息方向。M6 的协议工作集中在恢复、安全和故障演练验收。

### 15.1 重连和补报

| 场景 | 协议要求 |
| --- | --- |
| 节点控制连接断开 | 节点保留未确认 `traffic_event`，重连后按主节点确认游标补报 |
| 主节点重启 | 节点重新 `hello` 后可收到补报要求；主节点按持久化事件幂等确认 |
| 序号重复 | 内容一致返回 `traffic_event_ack`，不得重复统计 |
| 序号内容冲突 | 返回协议错误或拒绝确认，记录中文安全告警；M6 已覆盖已确认序号的冲突重放 |
| 序号乱序 | 补报窗口内可接收，确认游标不得越过缺失序号 |

### 15.2 安全验收

| 验收项 | 协议通过标准 |
| --- | --- |
| 未配对节点 | 无有效节点证书时不能建立控制连接、领取任务或上报有效事件 |
| 证书过期 | TLS 握手或身份映射失败，节点不能继续控制会话 |
| 证书轮换 | 新证书生效后旧证书失效，旧会话关闭并写入审计 |
| 流量事件伪造 | 事件中的节点、授权、资产和请求 ID 不匹配时拒绝入账 |
| 日志安全 | 协议错误可记录完整客户端 IP 用于排障，但不得回显证书正文、私钥、下载令牌或本地路径 |

### 15.3 故障演练

M6 必须演练节点离线、同步中断、流量事件重复、流量事件乱序、证书过期和证书轮换。演练结果应记录请求 ID、节点 ID、任务 ID、事件序号和中文结论，不能记录敏感凭据。
